# INVENTORY v1.1 — быстрая автоматическая разгрузка сундуков (future GDD)

**Дата:** 06.11.2026  
**Решение владельца:** INV30-D09-A — **SCOPE APPROVED / DEFERRED TO INVENTORY v1.1**  
**Реализация Unreal/Blueprint:** NOT STARTED  
**Детальные игровые и технические правила авторазгрузки:** NOT APPROVED / OPEN

## 1. Жёсткая граница версий

- **Inventory v1.0:** только обычный **ручной перенос** предметов через утверждённые Core/Bag/External UI и Drag & Drop (INVENTORY-UX), с проверкой обоих inventories и атомарностью каждой операции. Само наличие утверждённого дизайна ручного переноса не означает его реализации в UE.
- **Inventory v1.1:** возможность **одним действием автоматически разгрузить выбранные предметы в подходящие сундуки на базе**. Механика сохранена в будущем GDD, **не обязательна** для завершения design gate и реализации Inventory v1.0.
- Не добавлять без согласования авторазгрузку в A17/A18, текущий исходный backlog или Blueprint. Не трактовать отложенную функцию как реализованную либо как dependency для ручного переноса.

## 2. Концепция будущей механики, пока НЕ утверждённые детали

Из исторического черновика [Inventory v0.4](../Design/INVENTORY_DESIGN_V04_DRAFT.md) сохранены для будущего обсуждения **идеи**, не решения:
- Кнопка/действие «Быстрая разгрузка» при нахождении на базе, когда подходящие сундуки доступны.
- Поиск подходящих сундуков для разрешённых ресурсов, с возможным приоритетом уже существующих совместимых стопок.
- Возможно исключать избранные предметы, активную экипировку, защищённые слоты и привязки, не разрушая ссылок Hotbar/GUID.
- Если ёмкости не хватает, неразмещённый остаток должен безопасно оставаться у игрока.
- Учитывать доступ/расстояние, destroyed/moved chest, stale Revision, смену собственности, двойное подтверждение, Save/Load и угрозу D07-B.
- Концептуально допустима последовательность отдельных успешных атомарных переносов с честно показанным частичным результатом, однако **не утверждено**, будет ли v1.1 разрешать частичный суммарный результат или требовать одной общей транзакции.

**Запрещено считать эти пункты утверждёнными правилами v1.1**. Требуется отдельный decision gate и согласование со всеми активными контрактами на момент будущей реализации.

## 3. Будущий design gate (OPEN)

Перед implementation определить:
1. **Scope предметов:** какие ItemId/категории разгружаются, что защищено (избранное, экипировка, Hotbar GUID/тип, квестовые/опасные вещи), разрешён ли перенос из Core и экипированного Bag.
2. **Получатели:** типы сундуков, фильтры, приоритет при нескольких сундуках, порядок заполнения совместимых стопок, детерминированность.
3. **Доступность:** критерии базы, расстояния, LoS, владельца, блокировки сундука; что происходит при смене Pawn/разрушении сундука.
4. **Транзакционность:** отдельные commits vs одна общая атомарная команда; ограничения веса и слотов, stale Revision, отмена при D07 ActiveThreat, двукратный input, partial success и корректное отображение итогов.
5. **Persistence:** DTO/Save/Load, сохранение GUID/StackId, связи с сундуком и отсутствие дублирования, интеграция с A36–A40; A36 v1 не менять задним числом.
6. **UX:** где находится кнопка, когда доступна, подтверждение или мгновенное действие, счётчики перенесённых/оставшихся и сообщения об ошибках.

## 4. Будущая матрица приёмки, все NOT RUN

- Ручной перенос v1.0 работает без авторазгрузки и без автоматической сортировки.
- На базе и вне базы: корректная доступность команды v1.1 по будущим правилам.
- Два сундука с существующими/отсутствующими стеками, недостаток слотов/веса, запретные предметы, опустевшие источники и нулевые количества.
- Стек/рюкзак не дублируются, сохраняются GUID/InventoryId/StackId и валидность Hotbar.
- Столкновение с угрозой D07 до/после commit, закрытие сундука, уничтожение/сдвиг контейнера, stale Revision, double input, rollback или корректный partial progress по **будущему** утверждённому контракту.
- Save/Load и reconnect/lifecycle не повторяют проведённую разгрузку.
- UE Blueprint compile, PIE, package и тесты производительности: NOT RUN.
