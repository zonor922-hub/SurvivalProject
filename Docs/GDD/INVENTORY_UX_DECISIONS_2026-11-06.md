# SurvivalProject — INVENTORY-UX: утверждённые правила инвентаря

**Дата фиксации:** 2026-11-06. **Статус:** DESIGN APPROVED для перечисленных ниже решений; IMPLEMENTATION NOT VERIFIED / NOT STARTED для нового функционала; TESTS NOT RUN. Это проектные требования, **не** отчёт о готовности Unreal или A17.1.

**Scope:** управление предметами, осмотр, сортировка, Hotbar, Core/Bag, взаимодействие с внешними контейнерами. Не переписывать текущие контракты A05–A12, A11, A15–A17 MVP, BP01, A36 v1 и исходный backlog; новые backend-команды проектировать и интегрировать отдельно. Существующие функции могут реализовывать только часть этих правил.

## 1. Инварианты и границы

- Ограничения одновременно по физическим слотам и MaxWeight каждого контейнера. Core и Bag являются отдельными inventories с собственными `InventoryId`, `Revision` и лимитами. Core: 12 слотов / 15 кг. Малый Bag: 8 слотов / 15 кг, собственная масса 1,5 кг; средний: 12 / 25 кг, масса 3 кг; большой: 18 / 40 кг, масса 5 кг. Масса самого рюкзака и содержимого влияет на переносимую массу персонажа; собственная масса Bag не расходует его внутренний MaxWeight. Мягкий порог комфорта персонажа 35 кг отдельный от жёстких лимитов контейнеров; порог комфортного веса утверждён в BP01, точные штрафы перегруза остаются открытыми.
- UI читает авторитетное состояние, но не владеет предметами и напрямую не изменяет Slots, GUID, количество, Revision или WorldDrops.
- Любое действие либо завершается полностью (включая оба контейнера/мировой объект, где применимо), либо отклоняется с неизменным состоянием; stale Revision, изменившийся Bag, отсутствие места/спавна и двойная команда не могут терять/дублировать предметы. Требуются отдельные транзакционные координаторы для новых multi-container/world сценариев; A11 `TryTransferExact` не считать такой общей атомарной транзакцией.
- Заявленные правила относятся к будущей функциональности. A17 MVP опубликован в PR #28. A17.1 UI Split/Merge/stale Revision опубликована через merged PR #37 (06.11.2026); локальные проверки описаны в её отчёте, но полный машинный пакет доказательств и Windows package не опубликованы. Blueprint compile / PIE / package именно по новым решениям INVENTORY-UX NOT RUN.

## 2. Drag & Drop, Split, Merge, Drop

| ID | DESIGN APPROVED |
|---|---|
| INVENTORY-SWAP-A | Обычный Drag на занятый несовместимым предметом слот мгновенно меняет стопки местами; GUID каждого экземпляра сохраняется. |
| INVENTORY-DRAG-MERGE | Обычный Drag на совместимую неполную стопку объединяет до MaxStack. При переполнении заполняет цель до MaxStack, остаток остаётся в исходной стопке. |
| INVENTORY-DRAG-FULL-B | Обычный Drag на полностью заполненную совместимую стопку обменивает стопки местами вместо отказа. |
| INVENTORY-DRAG-PARTIAL-C | Ctrl+Drag переносит ровно одну единицу; при необходимости создаёт корректную новую стопку/GUID; для точного количества есть отдельный Split с ручным вводом и автоматическим поиском свободного слота. |
| INVENTORY-CTRL-CONFLICT-A | Ctrl+Drag одной единицы на несовместимый занятый слот отклоняется без авто-переноса в другой слот. |
| INVENTORY-CTRL-FULL-A | Ctrl+Drag на совместимую полную стопку отклоняется без swap. |
| INVENTORY-DRAG-DROP | Обычный Drag из инвентаря **за пределы окна** предлагает/осуществляет выброс 1 единицы по правилам операции; Shift+Drag за пределы окна — целую стопку. Отпускание внутри окна вне слота отменяет действие. Невозможный spawn/commit не удаляет предмет из inventory. |
| INVENTORY-SPLIT-UI | Split выбирает точное введённое количество (например, 10→7+3), UI самостоятельно находит свободный слот; backend A10 `TrySplit` с обязательным `TargetSlot` не изменяется молча. |
| INVENTORY-TRANSFER-CAPACITY-A | Обычный Drag целой стопки в пустой слот другого контейнера при нехватке веса/места отменяется целиком; частичный перенос отдельно через Split/Ctrl+Drag. Частичное объединение на совместимом неполном слоте сохраняется как исключение в пределах реально допустимой массы и MaxStack. |

Слот-источник = слот-цель: no-op. Обычный Drag в пустую ячейку переносит стопку; Ctrl+Drag в пустую — одну единицу при соблюдении правил. Проверки ItemId/качества/прочности/других индивидуальных параметров для StackCompatibility обязательны; отказ не меняет Revision.

### INV30-D02-A — отдельный частичный Merge и GUID (утверждено владельцем 06.11.2026)

**Статус: DESIGN APPROVED / NEW API NOT IMPLEMENTED.** Подтверждено решение D02 **A**: старую публичную A10 команду `TryMerge(SourceStackId, TargetStackId)` **не изменять**. Она по-прежнему переносит **всю** исходную стопку либо отклоняет операцию (в частности при `MaxStackExceeded`), сохраняет GUID цели и освобождает слот источника. Существующая A17.1 продолжает использовать только опубликованные API A10; запрещено молча менять её семантику.

Для нового INVENTORY-UX Drag-merge нужен **отдельный публичный API частичного объединения** (рабочее название `TryMergePartial`; окончательная сигнатура и способ координации Core/Bag/external определяются в отдельной технической задаче). UI отправляет команду, но сам не изменяет Slots, количество, GUID, Revision или массу. **Для частичного Merge создаваемые/удаляемые GUID не нужны.**

**Нормативная семантика:**
1. Оба идентификатора стопок должны существовать, быть различными, принадлежать действительным источнику/цели и иметь совместимые `ItemId`, `HasDurability`, активную `Durability` и другие применимые индивидуальные свойства. Проверяются текущее состояние, Expected Revision всех затронутых inventories, guard, MaxStack, физические Slots/MaxWeight и наличие прав доступа к целевому контейнеру. Stale/Busy/невалидная цель → отказ без изменений.
2. На Drag в совместимую **неполную** цель перемещается только вместившееся количество: `Moved = min(SourceQty, MaxStack - TargetQty)`, с дополнительным ограничением по реальной допустимой вместимости принимающего контейнера для межконтейнерного случая. Для подтверждённого `15+8→20+3` **цель** остаётся в своём слоте с `20` и **своим прежним GUID A**; **источник** остаётся **в прежнем исходном слоте**, с `3` и **своим прежним GUID B**. Третий слот не создаётся.
3. При **полном** переносе источника в совместимую цель (например, `12+8→20`) цель сохраняет свой GUID, исходная стопка исчезает, её прежний GUID **выводится из активного состояния**, исходный слот становится канонически пустым. Это не изменение поведения старой A10 `TryMerge`.
4. При цели, уже заполненной до MaxStack, **новый частичный Merge не выполняется**; предусмотренный INVENTORY-UX обычный Drag использует свою отдельную операцию swap. Неверная совместимость, отсутствие разрешённого количества или состояние источника=цель не создают commit или изменение Revision.
5. При одной затронутой inventory — ровно **один атомарный commit**, Revision +1 и одно итоговое уведомление после commit; при двух inventories требуется **единая атомарная межконтейнерная транзакция** с валидацией обеих Expected Revision до фиксации, без промежуточно наблюдаемого частичного успеха. Нельзя считать A11 `TryTransferExact` таким координатором автоматически. При отказе Slots, количества, веса, GUID, доступности внешнего контейнера, ошибке commit или повторном/stale запросе **обе** стороны неизменны: количество, вес, GUID, слоты, Revision и события успеха.
6. После успешной операции Hotbar и другие ссылки проверяют **фактический сохранившийся GUID**: при частичном Merge оба GUID остаются действительными; при полном исчезнувший GUID не переназначается произвольно на другой предмет. Ссылки на выведенный из активного состояния GUID должны безопасно инвалидироваться по действующему INVENTORY-UX. Отдельная политика сохранения/переназначения GUID при **Compact** этим решением **не утверждена** и остаётся OPEN.
7. `TrySplit` A10 по-прежнему создаёт новый GUID выделенной стопки; ручное количество и автоматический поиск пустого слота остаются задачей UI/координатора A17.1 без изменения сигнатуры `TrySplit`.

**Контрольная приёмка (тесты NOT RUN):** 15+8→20+3 с неизменными GUID и слотом остатка; 12+8→20 с инвалидированным исходным GUID; несовместимые ItemId/прочность; полная цель и отдельный Drag swap; stale Revision/Busy; неверные GUID; двойной запрос; сохранение количества/массы; отказ на превышении MaxWeight Core/Bag/External; один commit для одного inventory и атомарный commit обеих сторон для разных; контроль Hotbar на удалённый GUID; регрессия A10 `TryMerge` full-only и A17.1 UI.

**Границы:** только GDD. Новая команда, backend, Blueprint, PIE, package, A05–A12, A11, A17.1 и A36 v1 **не изменены**; новая реализация требует отдельного implementation PR и исполняемых тестов. [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).

**Исторический контекст:** спор из DOC02 о «новом слоте» завершён именно для нового Drag partial Merge: остаток остаётся в исходной существующей стопке. Это не переписывает исторический журнал и не превращает новые правила в реализацию.


## 3. Контекстное меню, осмотр, использование и экипировка

- **INVENTORY-CONTEXT-MENU-B:** показывать только применимые команды: «Осмотреть» (всегда), «Использовать», «Экипировать», «Разделить» (количество >1), «Выбросить 1», «Выбросить стопку». Неприменимые пункты скрываются; Merge выполняется Drag & Drop, не отдельной кнопкой контекстного меню.
- **INVENTORY-INSPECT / INSPECT-UI-B:** справа от сеток отображается подробная боковая панель, не перекрывающая инвентарь; можно выбирать другие предметы без закрытия. Поля: название, иконка, описание, тип, редкость, качество, масса, количество, характеристики, состояние/прочность и применимые свойства; несуществующие/неприменимые поля скрывать.
- **INVENTORY-INSPECT-COMPARE-B:** оружие, броню и инструменты автоматически сравнивать с подходящей уже экипированной вещью. Показывать разницу по сопоставимым характеристикам, где «лучше/хуже» определяется смыслом статов; при отсутствии подходящей экипировки сравнение скрыто. Просмотр не экипирует предмет.
- **INVENTORY-USE-B:** обычные расходники применяются сразу, особо опасные или ценные необратимые действия требуют подтверждения; точные критерии предупреждения ещё требуют проектирования.
- **INVENTORY-EQUIP-SWAP-A:** новое обычное снаряжение автоматически заменяет старое; прежний экземпляр атомарно возвращается в доступный inventory, иначе полный отказ с rollback. Сохраняются GUID, durability, stats и Revision. Надетый рюкзак с содержимым исключён из общей операции и регулируется BP01.
- **INVENTORY-UNEQUIP-B:** снятый обычный предмет сначала пытаемся поместить в Core; fallback на надетый Bag исключительно при ошибках вместимости Core (SlotsFull/WeightLimit), а не при Busy/NotReady/InvalidItem и иных неёмкостных ошибках. При невозможности обеих попыток — полный отказ. Рюкзаки с содержимым обрабатываются отдельно по BP01.

## 4. Сортировка и уплотнение

- **INVENTORY-SORT-B:** порядок предметов всегда ручной до явной команды «Сортировать». Доступные варианты: по типу/категории, по названию, по количеству, по редкости и качеству. Нет автоматической сортировки после pickup и нет режима сортировки по весу.
- **INVENTORY-SORT-RARITY-B:** для соответствующего режима редкость по убыванию, затем качество по убыванию при одинаковой редкости. Список tier редкости и формула качества отдельно не утверждались.
- **INVENTORY-SORT-SCOPE-A:** у Core и экипированного Bag самостоятельные кнопки «Сортировать», операции не перемещают предметы между inventories.
- **INVENTORY-SORT-COMPACT-C:** «Сортировать» только упорядочивает, а отдельная кнопка «Уплотнить» объединяет совместимые стопки до MaxStack. Уплотнение выполняется независимо в каждом контейнере, с сохранением количества/массы, транзакционной проверкой Revision и надлежащей обработкой GUID исчезнувших стопок. Не допускать нарушения Hotbar GUID-привязок; правило переназначения GUID для уплотнения остаётся техническим вопросом, а не разрешением подменять предмет.

## 5. Hotbar (8 быстрых слотов)

- **INVENTORY-HOTBAR-BIND-C / SLOTS-B:** 8 слотов, клавиши 1–8. Оружие, инструменты и обычное экипируемое снаряжение привязаны к **конкретному GUID**; еда и обычные расходники — к **ItemId/типу**. Ссылки не создают дополнительные предметы; поиск расходника охватывает Core и надетый Bag.
- **INVENTORY-HOTBAR-ACTIVATE-B:** клавиши 1–8 немедленно экипируют/активируют доступный инструмент/оружие либо используют обычный расходник. Колесо мыши **лишь выбирает** слот, ничего не потребляет. Потенциально опасные действия соблюдают правило подтверждения USE-B.
- **INVENTORY-HOTBAR-DRAG-A:** Drag из inventory на пустой слот создаёт привязку, на занятый заменяет прежнюю привязку. Ctrl/Shift не меняют число предметов при назначении на Hotbar.
- **INVENTORY-HOTBAR-MOVE-A:** Hotbar→пустой Hotbar перемещает привязку; Hotbar→занятый Hotbar **обменивает две привязки**. Перетаскивание привязки **за границу Hotbar** удаляет лишь привязку («Убрать с панели»), **никогда не выбрасывает физический предмет в мир**.
- **INVENTORY-HOTBAR-EMPTY-B:** у расходников с привязкой по типу при количестве 0 слот сохраняется, иконка затемняется и показывает 0; при новом экземпляре того же типа слот автоматически снова работает.
- **INVENTORY-HOTBAR-BROKEN-B:** сломанный конкретный инструмент/оружие (durability=0) сохраняет GUID-привязку; иконка затемняется/маркируется, использование запрещено до ремонта **этого же экземпляра**. Автоподмена аналогом запрещена.
- **INVENTORY-HOTBAR-OWNERSHIP-A:** перемещение GUID-предмета между Core и Bag или их слотами сохраняет привязку. Выброс в мир, помещение в сундук или уничтожение удаляют её. Автоподмена другим GUID запрещена. Типовые расходники подчиняются собственному EMPTY-B; конкретный физический стек не закреплён.
- Кэш/UI не должен скрывать потерю GUID, изменение владельца или stale Revision. Save/Load и lifecycle требуют отдельной технической спецификации.

## 6. Core + Bag + внешние контейнеры

- **INVENTORY-CORE-BAG-UI-A:** Core слева, экипированный Bag справа, показываются одновременно. У каждого собственные слоты, вес, InventoryId и отдельные действия «Сортировать»/«Уплотнить».
- **INVENTORY-BAG-UI-STATE-A:** если Bag не экипирован, его панель **полностью скрыта**. Успешная смена/снятие/экипировка Bag обновляет UI с актуальным InventoryId и отменяет незавершённый Drag, не меняя Core. Отказ в смене сохраняет прежнюю панель. BP01-политика самого снятия/замены не пересматривается.
- **INVENTORY-CORE-BAG-TRANSFER-A:** Drag несовместимых вещей между Core и Bag на занятые слоты выполняет атомарный swap **только** если оба resulting inventories удовлетворяют слотовым и весовым лимитам; иначе оба состояния неизменны. Для совместимых вещей действует merge и его отдельная capacity-проверка.
- **INVENTORY-WORLD-BAG-UI-A:** лежащий в мире рюкзак открывается как внешний контейнер рядом с Core без обязательной экипировки; перемещение Drag & Drop, собственный InventoryId/Revision. Это не разрешение обходить BP01 pickup/equip/drop.
- **INVENTORY-EXTERNAL-LAYOUT-A:** если есть экипированный Bag, при открытии внешнего контейнера одновременные панели **Core + Bag + внешний контейнер**; если Bag отсутствует, две панели. Все контейнеры раздельные, с собственными параметрами.
- **INVENTORY-EXTERNAL-TRANSFER-A:** прямой Drag & Drop между **любой парой** видимых Core, надетого Bag и внешнего контейнера, без промежуточного переноса через Core. Любые move/swap/merge должны проверять оба inventories и атомарно фиксироваться либо отклоняться; не расширять A11 молча. Само открытие обычного сундука и правила доступа/дистанции ещё требуют отдельного решения.
- BP01: полный рюкзак может быть оставлен в мире с содержимым; Core→Bag при автоматическом WorldPickup **только** при Core SlotsFull/WeightLimit, иных fallback нет. Маршрут S1 Exact→S2/P1 Exact двумя контейнерами пока roadmap, S3 partial world pickup не утверждён. Нельзя подменять это ручным Drag/transfer UX.

### INV30-D12-A — сеть хранилищ Эха вне Inventory v1.0 (утверждено 06.11.2026)

**SCOPE APPROVED / FUTURE SEPARATE SYSTEM; RULES NOT FULLY DESIGNED; UE NOT IMPLEMENTED.** Inventory v1.0 не включает связанное удалённое использование ресурсов и сетевые Узлы Эха; обычный ручной доступ к внешним контейнерам остаётся как утверждён в разделе 6. D12 **не является blocker** завершения v1.0.

- В будущей сети физические ресурсы **остаются в сундуках**, не копируются в общий виртуальный инвентарь.
- Доступ к связанным сундукам для будущего крафта/строительства предоставляется только через **действующий Узел Эха**. Отключение Узла отнимает сетевой доступ, но **не меняет** содержимое хранилищ.
- Любая будущая операция с несколькими сундуками требует **единой атомарной multi-inventory транзакции** и защиты от потерь/дубликатов; независимые вызовы A11 нельзя выдавать за общую транзакцию.
- **Детали сети OPEN:** радиус, подключение/фильтры сундуков, разрешения, операции, UI, стоимость/энергия, крафт/строительство, API, rollback и Save DTO. Никакого расширения A36 v1 или исходного backlog.
- Концепция и будущие тесты зафиксированы в [D12 future GDD: сеть хранилищ Эха](ECHO_STORAGE_NETWORK_D12_FUTURE_2026-11-06.md), без одобрения ещё не обсуждённых правил.

## 7. Ошибки, синхронизация и события

- **INVENTORY-ERROR-UI-B:** краткое уведомление об отказе и временная красная подсветка проблемного слота/сетки/шкалы веса. Причины включают WeightLimit, SlotsFull, несовместимость, MaxStack, Busy/NotReady и stale Revision; без модального окна на каждую ошибку.
- **INVENTORY-LIVE-UPDATE-A:** изменение авторитетного состояния сразу обновляет Core, Bag, внешний контейнер (если открыт), Hotbar, массу, количества, прочность и панель осмотра. Выбор сохраняется **по GUID**, пока соответствующий предмет доступен в инвентарях персонажа; исчезновение GUID/потеря доступа сбрасывает выбор. Автоматическая сортировка не запускается.
- **Stale Revision:** команда отклоняется без побочных изменений; клиент перечитывает свежие snapshots, снимает устаревший выбор и отменяет устаревший Drag/контекстное действие. Контейнерный commit и Refresh происходят в правильном порядке, без визуального фантомного успеха.
- При прерывании/недоступности внешнего контейнера действие не должно завершаться по старому snapshot. Критерии расстояния/доступа внешних контейнеров **OPEN**. **D07-B о боевой угрозе утверждён ниже**; радиус агрессии, период выхода из угрозы и повторного открытия UI не назначать без отдельного решения.

### INV30-D07-B — активная угроза и прерывание выброса (решение владельца от 06.11.2026)

**Статус: DESIGN APPROVED / UE IMPLEMENTATION NOT STARTED.** Сигнал **ActiveThreat** для инвентаря наступает при любом из трёх событий:

1. Враг обнаружил персонажа **и начал преследование** (целевое агрессивное поведение подтверждено авторитетным состоянием AI, а не одним фактом нахождения в радиусе).
2. Враг **начал атаку** против персонажа (даже если попадание ещё не произошло).
3. Персонаж **получил урон** (не требуется дополнительно ждать подтверждения преследования).

**Само присутствие враждебного NPC рядом**, без преследования, атаки или полученного урона, **не является ActiveThreat** и не блокирует инвентарь. Не вводить произвольный радиус автоматического закрытия UI. Критерии окончания угрозы, debounce/cooldown, какие ещё виды интерфейсов прерываются, и возможность повторного открытия при ActiveThreat — отдельные OPEN решения; они не должны молча переопределить данное правило возникновения угрозы.

**Реакция инвентаря и транзакционная граница:**
- При новом ActiveThreat инвентарный UI **закрывается**, незавершённый Drag/диалог подтверждения выброса **отменяется**. Для ещё не завершённого выброса предмет (или полный физический Bag) и исходный `StackId`/`InventoryId` остаются у прежнего владельца; никаких изменений количества, массы, Revision, GUID, WorldDrops и успешных событий.
- Авторитетная команда выброса должна перед **атомарным commit** повторно проверить ActiveThreat, актуальные Expected Revision, владение, валидность места создания мирового объекта и отсутствие повторной команды. Если угроза возникла **до commit**, отказ с rollback полного кандидата, без появления предмета в мире или потери в inventory. Изменение только UI не считается гарантией безопасности: источник истины на стороне игровой транзакции.
- Если commit выброса **уже состоялся** и лишь **после этого** возникла ActiveThreat, **не откатывать** успешное действие и не возвращать предмет автоматически: он остаётся в мире; UI закрывается. Порядок commit и событий угрозы требуется явно определить как сериализованное авторитетное событие, чтобы две команды в одном кадре не давали двойного результата.
- Новая попытка/повторное подтверждение не может завершить старую отменённую транзакцию. Смена владельца Bag по D05, drop WorldPickup и ошибки/невалидный spawn D08 должны соблюдать те же запреты потери и дублирования. **D08-B теперь отдельно DESIGN APPROVED**: автоматический поиск ближайшей безопасной позиции в ограниченном радиусе для полного Bag; проверки поверхности/collision/воды/доступности, полный rollback при отсутствии точки, сохранение `EntityId`/`InventoryId`/`StackId` и содержимого. См. [BP01 D08-B (Draft PR #38)](https://github.com/zonor922-hub/SurvivalProject/pull/38). D07 по-прежнему определяет момент отмены относительно commit. Будущий физический бросок в духе Escape from Tarkov записан как DEFERRED, не как текущая реализация.
- Не менять утверждённый BP-OVERLOAD-A: при стоянии Stamina восстанавливается **даже при ActiveThreat**. ActiveThreat для выброса не равен штрафу перегруза или SLEEP01 Fatigue.

**Будущие проверки (все NOT RUN):** нейтрально проходящий рядом враг не закрывает UI; обнаружил и начал преследование → ActiveThreat; начало атаки без попадания → ActiveThreat; получен урон без преследования → ActiveThreat; угроза до подтверждения, во время подготовки и непосредственно перед commit → отмена/rollback и предмет остаётся; угроза после успешного commit → предмет остаётся в мире; повторное подтверждение/двойной input → нет дублей; смена владельца Bag/stale Revision → отказ без повреждения; при ActiveThreat стояние продолжает восстанавливать Stamina согласно BP-OVERLOAD-A; UE/PIE/package NOT RUN.

**Границы:** только GDD. Ни Blueprint, ни `A05–A12`, `A15`, `A17.1`, `A36 v1` или исходный backlog не изменены. Реализация требует отдельного review/test matrix и проверки интеграции AI/combat/UI/world drop. Связано с [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).
