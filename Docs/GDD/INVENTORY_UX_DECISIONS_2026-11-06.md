# SurvivalProject — INVENTORY-UX: утверждённые правила инвентаря

**Дата фиксации:** 2026-11-06. **Статус:** DESIGN APPROVED для перечисленных ниже решений; IMPLEMENTATION NOT VERIFIED / NOT STARTED для нового функционала; TESTS NOT RUN. Это проектные требования, **не** отчёт о готовности Unreal или A17.1.

**Scope:** управление предметами, осмотр, сортировка, Hotbar, Core/Bag, взаимодействие с внешними контейнерами. Не переписывать текущие контракты A05–A12, A11, A15–A17 MVP, BP01, A36 v1 и исходный backlog; новые backend-команды проектировать и интегрировать отдельно. Существующие функции могут реализовывать только часть этих правил.

## 1. Инварианты и границы

- Ограничения одновременно по физическим слотам и MaxWeight каждого контейнера. Core и Bag являются отдельными inventories с собственными `InventoryId`, `Revision` и лимитами. Core: 12 слотов / 15 кг. Малый Bag: 8 слотов / 15 кг, собственная масса 1,5 кг; средний: 12 / 25 кг, масса 3 кг; большой: 18 / 40 кг, масса 5 кг. Масса самого рюкзака и содержимого влияет на переносимую массу персонажа; собственная масса Bag не расходует его внутренний MaxWeight. Мягкий порог комфорта персонажа 35 кг отдельный от жёстких лимитов контейнеров; порог комфортного веса утверждён в BP01, точные штрафы перегруза остаются открытыми.
- UI читает авторитетное состояние, но не владеет предметами и напрямую не изменяет Slots, GUID, количество, Revision или WorldDrops.
- Любое действие либо завершается полностью (включая оба контейнера/мировой объект, где применимо), либо отклоняется с неизменным состоянием; stale Revision, изменившийся Bag, отсутствие места/спавна и двойная команда не могут терять/дублировать предметы. Требуются отдельные транзакционные координаторы для новых multi-container/world сценариев; A11 `TryTransferExact` не считать такой общей атомарной транзакцией.
- Заявленные правила относятся к будущей функциональности. A17 MVP опубликован в PR #28. A17.1 UI Split/Merge/stale Revision опубликована через merged PR #37 (06.11.2026); локальные проверки описаны в её отчёте, но полный машинный пакет доказательств и Windows package не опубликованы. Blueprint compile / PIE / package именно по новым решениям INVENTORY-UX NOT RUN.

## 2. Drag & Drop, Split, Merge, Drop

| INVENTORY-DRAG-MERGE | Обычный Drag на совместимую неполную стопку объединяет до MaxStack. При переполнении заполняет цель до MaxStack, остаток остаётся в исходной стопке. |
| INVENTORY-DRAG-FULL-B | Обычный Drag на полностью заполненную совместимую стопку обменивает стопки местами вместо отказа. |
| INVENTORY-DRAG-PARTIAL-C | Ctrl+Drag переносит ровно одну единицу; при необходимости создаёт корректную новую стопку/GUID; для точного количества есть отдельный Split с ручным вводом и автоматическим поиском свободного слота. |
| INVENTORY-CTRL-CONFLICT-A | Ctrl+Drag одной единицы на несовместимый занятый слот отклоняется без авто-переноса в другой слот. |

| INVENTORY-DRAG-DROP | Обычный Drag из инвентаря **за пределы окна** предлагает/осуществляет выброс 1 единицы по правилам операции; Shift+Drag за пределы окна — целую стопку. Отпускание внутри окна вне слота отменяет действие. Невозможный spawn/commit не удаляет предмет из inventory. |
| INVENTORY-SPLIT-UI | Split выбирает точное введённое количество (например, 10→7+3), UI самостоятельно находит свободный слот; backend A10 `TrySplit` с обязательным `TargetSlot` не изменяется молча. |
| INVENTORY-TRANSFER-CAPACITY-A | Обычный Drag целой стопки в пустой слот другого контейнера при нехватке веса/места отменяется целиком; частичный перенос отдельно через Split/Ctrl+Drag. Частичное объединение на совместимом неполном слоте сохраняется как исключение в пределах реально допустимой массы и MaxStack. |

Слот-источник = слот-цель: no-op. Обычный Drag в пустую ячейку переносит стопку; Ctrl+Drag в пустую — одну единицу при соблюдении правил. Проверки ItemId/качества/прочности/других индивидуальных параметров для StackCompatibility обязательны; отказ не меняет Revision.

### INV30-D02-A — отдельный частичный Merge и GUID (утверждено владельцем 06.11.2026)

**Статус: DESIGN APPROVED / NEW API NOT IMPLEMENTED.** Подтверждено решение D02 **A**: старую публичную A10 команду `TryMerge(SourceStackId, TargetStackId)` **не изменять**. Она по-прежнему переносит **всю** исходную стопку либо отклоняет операцию (в частности при `MaxStackExceeded`), сохраняет GUID цели и освобождает слот источника. Существующая A17.1 продолжает использовать только опубликованные API A10; запрещено молча менять её семантику.

Для нового INVENTORY-UX Drag-merge нужен **отдельный публичный API частичного объединения** (рабочее название `TryMergePartial`; окончательная сигнатура и способ координации Core/Bag/external определяются в отдельной технической задаче). UI отправляет команду, но сам не изменяет Slots, количество, GUID, Revision или массу. **Для частичного Merge создаваемые/удаляемые GUID не нужны.**

**Нормативная семантика:**
1. Оба идентификатора стопок должны существовать, быть различными, принадлежать действительным источнику/цели и иметь совместимые `ItemId`, `HasDurability`, активную `Durability` и другие применимые индивидуальные свойства. Проверяются текущее состояние, Expected Revision всех затронутых inventories, guard, MaxStack, физические Slots/MaxWeight и наличие прав доступа к целевому контейнеру. Stale/Busy/невалидная цель → отказ без изменений.
2. На Drag в совместимую **неполную** цель перемещается только вместившееся количество: `Moved = min(SourceQty, MaxStack - TargetQty)`, с дополнительным ограничением по реальной допустимой вместимости принимающего контейнера для межконтейнерного случая. Для подтверждённого `15+8→20+3` **цель** остаётся в своём слоте с `20` и **своим прежним GUID A**; **источник** остаётся **в прежнем исходном слоте**, с `3` и **своим прежним GUID B**. Третий слот не создаётся.
3. При **полном** переносе источника в совместимую цель (например, `12+8→20`) цель сохраняет свой GUID, исходная стопка исчезает, её прежний GUID **выводится из активного состояния**, исходный слот становится канонически пустым. Это не изменение поведения старой A10 `TryMerge`.
4. При цели, уже заполненной до MaxStack, **новый частичный Merge не выполняется**; предусмотренный INVENTORY-UX обычный Drag использует свою отдельную операцию swap. Неверная совместимость, отсутствие разрешённого количества или состояние источника=цель не создают commit или изменение Revision.
5. При одной затронутой inventory — ровно **один атомарный commit**, Revision +1 и одно итоговое уведомление после commit; при двух inventories требуется **единая атомарная межконтейнерная транзакция** с валидацией обеих Expected Revision до фиксации, без промежуточно наблюдаемого частичного успеха. Нельзя считать A11 `TryTransferExact` таким координатором автоматически. При отказе Slots, количества, веса, GUID, доступности внешнего контейнера, ошибке commit или повторном/stale запросе **обе** стороны неизменны: количество, вес, GUID, слоты, Revision и события успеха.
6. После успешной операции Hotbar и другие ссылки проверяют **фактический сохранившийся GUID**: при частичном Merge оба GUID остаются действительными; при полном исчезнувший GUID не переназначается произвольно на другой предмет. Ссылки на выведенный из активного состояния GUID должны безопасно инвалидироваться по действующему INVENTORY-UX. Отдельная политика сохранения/переназначения GUID при **Compact** этим решением **не утверждена** и остаётся OPEN.
7. `TrySplit` A10 по-прежнему создаёт новый GUID выделенной стопки; ручное количество и автоматический поиск пустого слота остаются задачей UI/координатора A17.1 без изменения сигнатуры `TrySplit`.

**Контрольная приёмка (тесты NOT RUN):** 15+8→20+3 с неизменными GUID и слотом остатка; 12+8→20 с инвалидированным исходным GUID; несовместимые ItemId/прочность; полная цель и отдельный Drag swap; stale Revision/Busy; неверные GUID; двойной запрос; сохранение количества/массы; отказ на превышении MaxWeight Core/Bag/External; один commit для одного inventory и атомарный commit обеих сторон для разных; контроль Hotbar на удалённый GUID; регрессия A10 `TryMerge` full-only и A17.1 UI.

**Границы:** только GDD. Новая команда, backend, Blueprint, PIE, package, A05–A12, A11, A17.1 и A36 v1 **не изменены**; новая реализация требует отдельного implementation PR и исполняемых тестов. [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).

**Исторический контекст:** спор из DOC02 о «новом слоте» завершён именно для нового Drag partial Merge: остаток остаётся в исходной существующей стопке. Это не переписывает исторический журнал и не превращает новые правила в реализацию.


## 3. Контекстное меню, осмотр, использование и экипировка

- **INVENTORY-CONTEXT-MENU-B:** показывать только применимые команды: «Осмотреть» (всегда), «Использовать», «Экипировать», «Разделить» (количество >1), «Выбросить 1», «Выбросить стопку». Неприменимые пункты скрываются; Merge выполняется Drag & Drop, не отдельной кнопкой контекстного меню.
- **INVENTORY-INSPECT / INSPECT-UI-B:** справа от сеток отображается подробная боковая панель, не перекрывающая инвентарь; можно выбирать другие предметы без закрытия. Поля: название, иконка, описание, тип, редкость, качество, масса, количество, характеристики, состояние/прочность и применимые свойства; несуществующие/неприменимые поля скрывать.
- **INVENTORY-INSPECT-COMPARE-B:** оружие, броню и инструменты автоматически сравнивать с подходящей уже экипированной вещью. Показывать разницу по сопоставимым характеристикам, где «лучше/хуже» определяется смыслом статов; при отсутствии подходящей экипировки сравнение скрыто. Просмотр не экипирует предмет.
- **INVENTORY-USE-B / INV30-USE-CONFIRM-A:** обычные расходники применяются сразу; подтверждение опасного или необратимого использования определяется **явным флагом `ConfirmOnUse` у конкретного действия предмета**, а не автоматическим выводом по редкости. Нормативный технический контракт утверждён ниже.
- **INVENTORY-EQUIP-SWAP-A:** новое обычное снаряжение автоматически заменяет старое; прежний экземпляр атомарно возвращается в доступный inventory, иначе полный отказ с rollback. Сохраняются GUID, durability, stats и Revision. Надетый рюкзак с содержимым исключён из общей операции и регулируется BP01.
- **INVENTORY-UNEQUIP-B:** снятый обычный предмет сначала пытаемся поместить в Core; fallback на надетый Bag исключительно при ошибках вместимости Core (SlotsFull/WeightLimit), а не при Busy/NotReady/InvalidItem и иных неёмкостных ошибках. При невозможности обеих попыток — полный отказ. Рюкзаки с содержимым обрабатываются отдельно по BP01.

### INV30-USE-CONFIRM-A — явный ConfirmOnUse действия (утверждено 06.11.2026)

**DESIGN APPROVED / IMPLEMENTATION NOT STARTED.** Для каждой операции «Использовать» конкретного ItemId/экземпляра предусмотрен **явный признак `ConfirmOnUse` именно у действия**, а не универсальный вывод из редкости, цены, класса или типа предмета.

- **Обычные расходники:** если действие не помечено `ConfirmOnUse`, обычное использование выполняется **сразу**, без лишнего модального подтверждения, через обычную проверяемую авторитетную команду. **Редкость, качество или высокая стоимость сами по себе не включают диалог.**
- **Опасные, особо ценные необратимые действия:** дизайнер контента отдельно помечает нужное **действие** флагом `ConfirmOnUse=true`; только при таком флаге UI показывает подтверждение с идентификацией действия и предмета. Разные действия одного предмета могут иметь разные требования подтверждения. Конкретный перечень ItemId/ActionId/опасных действий **не утверждён** этой записью.
- **Подтверждение не является commit**: до выбора «Подтвердить» никакое количество, Revision, содержимое, durability, GUID, статус мира или эффект действия не изменяются. Отмена/закрытие меню не потребляет предмет и не вызывает действие.
- **Повторная авторитетная проверка при подтверждении**: разрешённый `ActionId`, ожидаемые `ItemId` и, где применимо, `StackId/GUID` конкретного экземпляра; актуальные `InventoryId`/ownership, доступность и применимость действия, живое/разрешённое состояние исполнителя, нужное количество, активная `Revision` всех затронутых inventories и mutation guard. Смена предмета, контейнера, владельца или Revision с момента открытия диалога → **отказ/stale**, закрытие старого подтверждения и обновление UI, а не выполнение на новом предмете. Для ItemId-Hotbar расходников выбор конкретного доступного стака сохраняется отдельным OPEN design gate; нельзя использовать невалидную или чужую стопку.
- **Атомарность и идемпотентность**: двойное подтверждение, повторный input/Hotbar, гонка сети или повтор после stale не должны дважды расходовать предмет, начислять эффект или публиковать успешное событие. В одной авторитетной операции изменение ресурса и применение эффекта завершаются вместе либо полностью отклоняются **до commit**; ошибки/невозможность применения возвращают исходное состояние. Конкретный transaction coordinator/use-effect interface и обработка необратимых внешних эффектов остаются технической задачей.
- **Совместимость D07/BP01:** доступность предмета, режим угрозы, отмена открытого UI и lifecycle не обходятся через `ConfirmOnUse`; если UI закрыт из-за угрозы **до commit**, незавершённое подтверждение отменено, ничего не потребляется. Успешное уже committed действие не откатывается автоматически после угрозы. Не менять остальные решения для боевого поведения без отдельного разрешения.
- **Hotbar и контекстное меню** применяют одинаковую проверку `ConfirmOnUse` и один авторитетный механизм использования. Нельзя обходить подтверждение через клавиши 1–8. `ConfirmOnUse` не вводит новых физических предметов или GUID.

**Будущие проверки (все NOT RUN):** обычный расходник без флага используется сразу; редкий/дорогой предмет без флага не показывает диалог; два действия одного предмета с разными `ConfirmOnUse`; помеченное действие требует подтверждения как из контекстного меню, так и из Hotbar; отмена и закрытие диалога не меняют состояние; смена ItemId/StackId/GUID, ownership, доступности и Revision до подтверждения приводит к отказу без расхода; двойное нажатие, stale retry, параллельные команды дают максимум один эффект/расход; невозможность применения до commit откатывает всё; угроза D07 до commit отменяет действие; успешный commit не откатывается от более поздней угрозы; Save/Load не повторяет уже committed эффекты. UE Blueprint compile, PIE, Windows package **NOT RUN**.

**Границы:** изменение исключительно GDD; существующие A05–A12/A17.1/A36 v1, Blueprint, исходный backlog и item-data assets **не изменены**. Схема определения `ConfirmOnUse` в игровых данных, перечень опасных действий, точная сигнатура Use API/DTO и техническая обработка side-effects требуют будущей реализации и тестов. См. [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).

## 4. Сортировка и уплотнение

- **INVENTORY-SORT-B:** порядок предметов всегда ручной до явной команды «Сортировать». Доступные варианты: по типу/категории, по названию, по количеству, по редкости и качеству. Нет автоматической сортировки после pickup и нет режима сортировки по весу.
- **INVENTORY-SORT-RARITY-B:** для соответствующего режима редкость по убыванию, затем качество по убыванию при одинаковой редкости. Список tier редкости и формула качества отдельно не утверждались.
- **INVENTORY-SORT-SCOPE-A:** у Core и экипированного Bag самостоятельные кнопки «Сортировать», операции не перемещают предметы между inventories.
- **INVENTORY-SORT-COMPACT-C:** «Сортировать» только упорядочивает, а отдельная кнопка «Уплотнить» объединяет совместимые стопки до MaxStack. Уплотнение выполняется **независимо в каждом контейнере**, с сохранением количества/массы и проверкой Revision; утверждённую политику GUID и Hotbar фиксирует **INV30-COMPACT-GUID-A** ниже.

### INV30-COMPACT-GUID-A — утверждённая политика GUID при «Уплотнить» (06.11.2026)

**DESIGN APPROVED / NEW COMPACT BACKEND NOT IMPLEMENTED.** При объединении нескольких совместимых стопок в рамках команды **«Уплотнить»** применяются следующие инварианты:

- **GUID целевой/сохранившейся стопки остаётся прежним.** Перемещение количества из другой стопки в эту цель само по себе не создаёт новый StackId. В случае частичного поглощения остаток источника сохраняет **свой** GUID, пока его количество положительно; правило отдельного partial Drag-merge D02-A сохраняется.
- Когда источник поглощён **полностью**, его стопка исчезает, слот становится пустым, прежний GUID **выводится из активного состояния**. Запрещено повторно выдавать или подменять этот GUID внутри операции. Нет «нового слота» для нулевого остатка.
- **Никакого автоматического переназначения ссылок** на GUID поглощённых стопок на целевой GUID, даже при равенстве ItemId. Ссылки Inspect/выбора, Hotbar и иные GUID-зависимые ссылки должны безопасно обнаруживать исчезновение и инвалидироваться согласно своему жизненному циклу, без подмены другого экземпляра.
- **Hotbar (уже утверждённый контракт):** обычные расходники, включая еду, привязаны **по ItemId** и продолжают работать с доступными стопками того же типа после Compact; конкретный порядок выбора расходной стопки **ещё OPEN**. Оружие, инструменты и индивидуальное снаряжение привязаны **по GUID**, не подставлять другой экземпляр в случае исчезновения GUID. Сломанный предмет с сохранившимся GUID остаётся привязанным, но заблокирован до ремонта этого же экземпляра.
- **Атомарность:** весь Compact одного конкретного InventoryId проверяет корректность слотов, StackCompatibility, MaxStack, жёсткие ограничения веса, ownership, mutation guard и актуальную **Expected Revision** до commit. При успешной реальной мутации выполняется **один итоговый commit / Revision+1 / уведомление после commit** для затронутого inventory; ни один промежуточный этап уплотнения не виден как завершённое состояние. При stale Revision, Busy, incompatibility, повреждённом GUID/слоте или ином отказе **количество, масса, StackId, слоты и Revision не меняются**, успешное событие не испускается. Если ничего уплотнять, допускается no-op без мутации.
- **Scope:** Core, надетый Bag и внешние контейнеры уплотняются **только по отдельной явной команде** каждый, без скрытого перемещения между inventories. Само уплотнение не запускает Sort и не меняет уже утверждённую логику старого A10 `TryMerge` (full-only), D02-A partial Drag-merge и A17.1. Выбор целевой стопки при нескольких совместимых кандидатах и точный алгоритм перебора остаются **техническими OPEN**, не меняя этих игровых инвариантов.
- **Persist/UI:** Save/Load и LiveUpdate должны сохранять итоговое уникальное множество активных GUID и корректные ссылки, без «воскрешения» поглощённых стопок, фантомного количества и автоматической перепривязки Hotbar. Детальные DTO/миграции согласуются отдельно, без ретроактивного изменения A36 v1.

**Будущие проверки (все NOT RUN):** `12(A)+8(B)→20(A)` и B больше не активен; `15(A)+8(B)→20(A)+3(B)` и оба GUID сохраняются; три и более стопки и несколько целевых slots; разные ItemId/quality/durability никогда не объединяются неправомерно; отсутствие изменения количества/суммарной массы; ItemId-Hotbar продолжает работать после смены числа стопок, GUID-Hotbar не переназначается; Inspect выбор для исчезнувшего GUID сбрасывается; stale Revision/Busy/превышение MaxStack и прерывание возвращают полный rollback; Revision и событие при успешном Compact ровно один раз, без мутации при no-op; отдельные Core/Bag/External, Save/Load и регрессия A10/A17.1. ## 5. Hotbar (8 быстрых слотов)

- **INVENTORY-HOTBAR-BIND-C / SLOTS-B:** 8 слотов, клавиши 1–8. Оружие, инструменты и обычное экипируемое снаряжение привязаны к **конкретному GUID**; еда и обычные расходники — к **ItemId/типу**. Ссылки не создают дополнительные предметы; поиск расходника охватывает Core и **только надетый** Bag. Приоритет выбора конкретной расходной стопки утверждён ниже как **INV30-HOTBAR-STACK-B**.
- **INVENTORY-HOTBAR-ACTIVATE-B:** клавиши 1–8 немедленно экипируют/активируют доступный инструмент/оружие либо используют обычный расходник. Колесо мыши **лишь выбирает** слот, ничего не потребляет. Потенциально опасные действия соблюдают правило подтверждения USE-B.
- **INVENTORY-HOTBAR-DRAG-A:** Drag из inventory на пустой слот создаёт привязку, на занятый заменяет прежнюю привязку. Ctrl/Shift не меняют число предметов при назначении на Hotbar.
- **INVENTORY-HOTBAR-MOVE-A:** Hotbar→пустой Hotbar перемещает привязку; Hotbar→занятый Hotbar **обменивает две привязки**. Перетаскивание привязки **за границу Hotbar** удаляет лишь привязку («Убрать с панели»), **никогда не выбрасывает физический предмет в мир**.
- **INVENTORY-HOTBAR-EMPTY-B:** у расходников с привязкой по типу при количестве 0 слот сохраняется, иконка затемняется и показывает 0; при новом экземпляре того же типа слот автоматически снова работает.
- **INVENTORY-HOTBAR-BROKEN-B:** сломанный конкретный инструмент/оружие (durability=0) сохраняет GUID-привязку; иконка затемняется/маркируется, использование запрещено до ремонта **этого же экземпляра**. Автоподмена аналогом запрещена.
- **INVENTORY-HOTBAR-OWNERSHIP-A:** перемещение GUID-предмета между Core и Bag или их слотами сохраняет привязку. Выброс в мир, помещение в сундук или уничтожение удаляют её. Автоподмена другим GUID запрещена. Типовые расходники подчиняются собственному EMPTY-B; конкретный физический стек не закреплён.
- Кэш/UI не должен скрывать потерю GUID, изменение владельца или stale Revision. Save/Load и lifecycle требуют отдельной технической спецификации.

### INV30-HOTBAR-STACK-B — приоритет расходной стопки по ItemId (06.11.2026)

**DESIGN APPROVED / IMPLEMENTATION NOT STARTED.** При активации в Hotbar обычного расходника, который привязан к **`ItemId`**, авторитетная игровая логика выбирает **одну конкретную доступную стопку этого ItemId** из текущего Core или надетого Bag, с предсказуемым приоритетом.

**Нормативный порядок выбора (один и тот же для меню использования через Hotbar и подтверждения):**
1. Отобрать только действительные, принадлежащие персонажу, доступные для использования стопки **нужного `ItemId` с положительным количеством** из Core и **актуального надетого** Bag. Ненадетый Bag, лежащий в мире Bag, внешние сундуки и сеть Эха **не участвуют**. Не считать UI-кэш авторитетным источником. Дополнительные специфические условия применимости действия должны быть проверены, как предписывает `USE-CONFIRM-A`.
2. **Выбрать наименьшее количество** среди подходящих стопок. При равном количестве приоритет **Core перед Bag**. При равенстве контейнера и количества выбрать стопку с **меньшим индексом слота**. Это детерминированная сортировка кандидатов по ключу `(Quantity ASC, ContainerPriority Core=0/Bag=1, SlotIndex ASC)`; произвольный порядок массива, Widget или GUID не должен влиять на результат.
3. Сохранить идентичность выбранного кандидата для данного запроса: `InventoryId`, `StackId/GUID`, `ItemId`, исходное количество, индекс слота, Expected `Revision` и необходимый `ActionId`. Hotbar остаётся **ItemId-ссылкой**, **не** превращается в GUID-привязку. Не перемещать автоматически предметы между контейнерами.
4. **Непосредственно перед commit** снова проверить `ItemId`, выбранные `StackId/GUID`, `InventoryId`, принадлежность и доступность/экипировку Bag, фактическое количество (должно хватать для действия), слот, Expected `Revision`, mutation guard и применимость `ActionId`. При stale Revision, смене владельца/Bag/слота, отсутствии достаточного количества или недействительном действии **отклонить без расхода, побочных эффектов и успешного события**; перечитать snapshot для новой отдельной попытки, **не перескакивая молча на другую стопку в старом запросе**.
5. Соблюдать **INV30-USE-CONFIRM-A**: если конкретное действие имеет `ConfirmOnUse=true`, выбор кандидата является частью ожидающего подтверждения, а проверка повторяется **после подтверждения перед commit**; редкость не добавляет подтверждение. Двойной input, двойное подтверждение и повтор запроса не вызывают второго расхода/эффекта; применение эффекта и изменение количества должны быть согласованно атомарными.
6. После расхода последней единицы отдельный StackId больше не активен по обычным инвариантам. **Hotbar EMPTY-B сохраняется:** при отсутствии подходящего количества ItemId в Core и надетом Bag привязка остаётся видимой, с `0` и затемнённой иконкой; появление предмета того же `ItemId` в одном из этих контейнеров делает слот снова доступным без перепривязки. ### INV30-EXTERNAL-ACCESS-A — доступ к сундуку по дистанции (утверждено 06.11.2026)

**DESIGN APPROVED / IMPLEMENTATION NOT STARTED.** Обычный внешний **сундук** разрешено открыть только в утверждаемой позже допустимой зоне взаимодействия. **Точное числовое значение радиуса — OPEN**, не вводить произвольные метры в нормативные требования.

- **Open:** при попытке открыть сундук проверить актуальную допустимую дистанцию до него и доступность целевого внешнего контейнера. За пределами допустимой зоны окно сундука не открывается, внешняя Inventory-сессия не создаёт разрешения на перенос. Конкретный origin/anchor для расстояния, геометрия и дополнительные критерии (например, LoS, права, блокировки) остаются отдельными техническими/дизайн-решениями.
- **Exit:** как только персонаж выходит за допустимый радиус, **немедленно** закрыть UI внешнего сундука, прекратить все новые операции с его InventoryId и **отменить ещё не завершённые Drag/Transfer/Swap/Merge/контекстные операции**, подготовленные в этой сессии. **Никакого grace period, задержки или автоматического удержания окна** за границей радиуса.
- **Commit boundary:** только состояние **до commit** можно отменить. Каждый backend-запрос к этому сундуку, включая уже поставленный в очередь, обязан до атомарного commit заново проверить актуальную дистанцию, допустимость доступа, ownership/InventoryId, mutation guards и Expected Revision затронутых inventories. Выход за радиус **до commit** → отказ/полный rollback без изменения количества, слотов, GUID, веса, Revision и без события успешного переноса; уже успешно **committed** переносы при последующем отходе **не откатываются** и остаются у нового владельца.
- **Concurrency:** закрытие UI не является единственной защитой; авторитетный транзакционный контур должен сериализовать проверку доступа и commit относительно выхода за радиус. Двойной ввод, запоздавший callback или подтверждение из закрытого окна не возобновляют отменённый запрос. Не допускать дублирования и потери вещей.
- **UI/Session:** при закрытии внешней панели отменить активную операцию, selection, target reference и stale snapshots **именно внешней сессии**, сохранив корректное авторитетное состояние Core/Bag и действующий видимый интерфейс по их общим правилам. Повторное приближение само по себе не даёт разрешения завершить старую операцию; повторное открытие сундука требует новой актуальной проверки. Правила общего UI при смене Pawn/Death/Load согласовать отдельно.
- **Интеграция:** сохраняются утверждённые `INVENTORY-EXTERNAL-LAYOUT-A`, прямой ручной transfer Core/Bag/External, D07-B ActiveThreat, D02-A GUID/Revision, D05-B физический Bag в сундуке, D09-A исключение авторазгрузки v1.0. Эта запись **не утверждает** точный радиус, LoS, сетевой доступ к удалённым сундукам или особые правила открытия лежащего в мире Bag; для world Bag требуются отдельные параметры доступности при реализации.

## 7. Ошибки, синхронизация и события

- **INVENTORY-ERROR-UI-B:** краткое уведомление об отказе и временная красная подсветка проблемного слота/сетки/шкалы веса. Причины включают WeightLimit, SlotsFull, несовместимость, MaxStack, Busy/NotReady и stale Revision; без модального окна на каждую ошибку.
- **INVENTORY-LIVE-UPDATE-A:** изменение авторитетного состояния сразу обновляет Core, Bag, внешний контейнер (если открыт), Hotbar, массу, количества, прочность и панель осмотра. Выбор сохраняется **по GUID**, пока соответствующий предмет доступен в инвентарях персонажа; исчезновение GUID/потеря доступа сбрасывает выбор. Автоматическая сортировка не запускается.
- **Stale Revision:** команда отклоняется без побочных изменений; клиент перечитывает свежие snapshots, снимает устаревший выбор и отменяет устаревший Drag/контекстное действие. Контейнерный commit и Refresh происходят в правильном порядке, без визуального фантомного успеха.
- При прерывании/недоступности внешнего контейнера действие не должно завершаться по старому snapshot. **Для обычных сундуков утверждён INV30-EXTERNAL-ACCESS-A:** доступ только в зоне взаимодействия, немедленное закрытие при выходе, запрет нового transfer и rollback незавершённого; завершённый commit не откатывать. **Точный радиус и дополнительные критерии доступа OPEN**. Для лежащего в мире Bag точные параметры отдельно OPEN. **D07-B о боевой угрозе утверждён ниже**; радиус агрессии, период выхода из угрозы и повторного открытия UI не назначать без отдельного решения.

### INV30-LIFECYCLE-A — закрытие UI и сброс сессии при DeathStarted / Pawn / Load (06.11.2026)

**DESIGN APPROVED / UE IMPLEMENTATION NOT STARTED.** При наступлении любого из событий **`DeathStarted`**, **смена `Pawn`** или **`OpenLevel/Load`** текущая клиентская сессия инвентаря **полностью завершается**, не переносится и автоматически не восстанавливается.

1. **Немедленно закрыть** UI Core/Bag, все внешние панели и сундуки, Inventory Context Menu, Inspect, Drag & Drop, выбор и модальные подтверждения (включая `ConfirmOnUse`); закрыть/сбросить состояние интерактивной инвентарной сессии. Это правило не уничтожает принадлежащие персонажу предметы и не является отдельной операцией DeathCache.
2. **Отменить все ещё не завершённые** команды, UI-подтверждения и подготовленные транзакции сессии: Split/Merge/Compact, move/swap/transfer, Use, equip/unequip, pickup/drop, доступ к WorldBag/сундуку и прочие операции, которые ещё не достигли **авторитетного commit**. Параметры, предварительно выбранные кандидаты и ожидающие подтверждения не подлежат автоматическому повтору после события.
3. **Инвалидировать** снимки `InventoryId`/`Revision`/slots, `StackId/GUID` выбранных экземпляров, `ActionId`/подтверждения, pending requests, указатели на внешние контейнеры/Actor и временную привязку к старому Pawn. Старые callbacks/ответы после смены сессии считаются устаревшими и не могут выполнять commit, повторно открывать панель или менять новый UI.
4. **Авторитетная граница:** закрытие Widget само по себе недостаточно. При каждом новом запросе и перед commit backend проверяет, что сессия/контекст Pawn и состояние мира всё ещё актуальны, с учётом `Expected Revision`, ownership, mutation guard и `DeathStarted/Load`. Запрос, не завершённый к моменту события, отклоняется **без частичной мутации/успешного события**. Порядок события lifecycle относительно commit должен быть сериализован в едином источнике истины; гонка в одном кадре не даёт двойного результата.
5. **Уже завершённый commit не откатывается.** Действие, авторитетно завершённое **до** события, сохраняется в мировом/инвентарном состоянии, а далее подчиняется обычным DEATH01/Load правилам. В частности, завершённый **до `DeathStarted`** pickup входит в носимое имущество, которое обрабатывает целевая модель смерти; незавершённый pickup не должен быть перенесён в неё. Это **не страховка вещей после смерти** и не отмена потери носимого имущества.
6. **Новое открытие:** после завершения смены Pawn или Load инвентарь разрешено открыть **только новым явным действием игрока**, на базе **нового актуального авторитетного snapshot**. Нельзя автоматически восстанавливать старую вкладку, выделение, внешний сундук, Drag или подтверждение. Валидность нового Pawn, готовность восстановленного мира и доступность каждого внешнего контейнера проверяются заново.
7. **DEATH01:** это решение управляет **UI/сессией и границей транзакций**, но **не** утверждает форму DeathCache, TTL потери или повторные смерти; они остаются отдельными открытыми проектными правилами DEATH01. Не менять уже согласованный принцип потери носимого имущества и атомарность его обработки. Сам `DeathStarted` запрещает новые инвентарные операции, пока lifecycle/Death-подсистема не разрешит их на новом валидном Pawn.
8. **A36 v1 и Save/Load:** **не менять архитектуру/DTO/SaveVersion 1 A36 v1**. Save не должен фиксировать промежуточный inventory commit; Load/OpenLevel уничтожает прошлую UI-сессию и прошлые Actor-ссылки. Сохранение завершённых состояний и восстановление мира определяет SaveCoordinator в будущей отдельной реализации, без применения устаревших UI snapshot к новому уровню. Новый Core/Bag/WorldBag/Hotbar DTO и согласование SaveVersion 2 являются отдельным technical/design gate.
9. **Hotbar:** существующие устойчивые привязки `ItemId`/`GUID` как предметные данные не должны автоматически уничтожаться из-за визуального сброса UI. После завершения lifecycle отображение и доступность Hotbar пересчитываются по новым авторитетным inventory/ownership; политика сохранения/утраты привязок при Death/новом Pawn/SaveGame требует отдельного DTO-контракта и не утверждается автоматически данным решением.

**Будущие проверки (все NOT RUN):** DeathStarted при открытом Core/Bag/external и незавершённом Split, Merge, Drag/Transfer, Drop, Use/ConfirmOnUse → UI закрыт, отказ без расхода/дубликатов; старые callbacks не оживляют виджеты и не меняют новый Pawn; завершённый до события commit не откатывается, при смерти имущество подчиняется DEATH01; Pawn switch во время Use/transfer, смена `InventoryId`/ownership и `Revision` → stale отказ; `OpenLevel/Load` при активной панели, повторная загрузка и pending command → UI не восстанавливается, дублей предметов/Actors нет; новое открытие только вручную по свежему snapshot; Save запрос во время активного mutation guard и промежуточного Death transfer не создаёт промежуточных DTO; регрессия D07-B ActiveThreat, External Access-A, HOTBAR-EMPTY-B, A10/A17.1 и A36. Blueprint compile/PIE/package **NOT RUN**.

**Открытые технические работы:** механизм токена/поколения сессии, идемпотентность pending requests и порядок autoritative событий, конкретные Save DTO/Hotbar policy для Death/Load, тестовые сценарии в UE. Этим решением **не** меняются Blueprint, C++, A05–A12, A36 v1, DEATH01, исходный backlog или статусы реализации. [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).

### INV30-D07-B — активная угроза и прерывание выброса (решение владельца от 06.11.2026)

**Статус: DESIGN APPROVED / UE IMPLEMENTATION NOT STARTED.** Сигнал **ActiveThreat** для инвентаря наступает при любом из трёх событий:

1. Враг обнаружил персонажа **и начал преследование** (целевое агрессивное поведение подтверждено авторитетным состоянием AI, а не одним фактом нахождения в радиусе).
2. Враг **начал атаку** против персонажа (даже если попадание ещё не произошло).
3. Персонаж **получил урон** (не требуется дополнительно ждать подтверждения преследования).

**Само присутствие враждебного NPC рядом**, без преследования, атаки или полученного урона, **не является ActiveThreat** и не блокирует инвентарь. Не вводить произвольный радиус автоматического закрытия UI. Критерии окончания угрозы, debounce/cooldown, какие ещё виды интерфейсов прерываются, и возможность повторного открытия при ActiveThreat — отдельные OPEN решения; они не должны молча переопределить данное правило возникновения угрозы.

**Реакция инвентаря и транзакционная граница:**
- При новом ActiveThreat инвентарный UI **закрывается**, незавершённый Drag/диалог подтверждения выброса **отменяется**. Для ещё не завершённого выброса предмет (или полный физический Bag) и исходный `StackId`/`InventoryId` остаются у прежнего владельца; никаких изменений количества, массы, Revision, GUID, WorldDrops и успешных событий.
- Авторитетная команда выброса должна перед **атомарным commit** повторно проверить ActiveThreat, актуальные Expected Revision, владение, валидность места создания мирового объекта и отсутствие повторной команды. Если угроза возникла **до commit**, отказ с rollback полного кандидата, без появления предмета в мире или потери в inventory. Изменение только UI не считается гарантией безопасности: источник истины на стороне игровой транзакции.
- Если commit выброса **уже состоялся** и лишь **после этого** возникла ActiveThreat, **не откатывать** успешное действие и не возвращать предмет автоматически: он остаётся в мире; UI закрывается. Порядок commit и событий угрозы требуется явно определить как сериализованное авторитетное событие, чтобы две команды в одном кадре не давали двойного результата.
- Новая попытка/повторное подтверждение не может завершить старую отменённую транзакцию. Смена владельца Bag по D05, drop WorldPickup и ошибки/невалидный spawn D08 должны соблюдать те же запреты потери и дублирования. **D08-B теперь отдельно DESIGN APPROVED**: автоматический поиск ближайшей безопасной позиции в ограниченном радиусе для полного Bag; проверки поверхности/collision/воды/доступности, полный rollback при отсутствии точки, сохранение `EntityId`/`InventoryId`/`StackId` и содержимого. См. [BP01 D08-B (Draft PR #38)](https://github.com/zonor922-hub/SurvivalProject/pull/38). D07 по-прежнему определяет момент отмены относительно commit. Будущий физический бросок в духе Escape from Tarkov записан как DEFERRED, не как текущая реализация.
- Не менять утверждённый BP-OVERLOAD-A: при стоянии Stamina восстанавливается **даже при ActiveThreat**. ActiveThreat для выброса не равен штрафу перегруза или SLEEP01 Fatigue.

**Будущие проверки (все NOT RUN):** нейтрально проходящий рядом враг не закрывает UI; обнаружил и начал преследование → ActiveThreat; начало атаки без попадания → ActiveThreat; получен урон без преследования → ActiveThreat; угроза до подтверждения, во время подготовки и непосредственно перед commit → отмена/rollback и предмет остаётся; угроза после успешного commit → предмет остаётся в мире; повторное подтверждение/двойной input → нет дублей; смена владельца Bag/stale Revision → отказ без повреждения; при ActiveThreat стояние продолжает восстанавливать Stamina согласно BP-OVERLOAD-A; UE/PIE/package NOT RUN.

**Границы:** только GDD. Ни Blueprint, ни `A05–A12`, `A15`, `A17.1`, `A36 v1` или исходный backlog не изменены. Реализация требует отдельного review/test matrix и проверки интеграции AI/combat/UI/world drop. Связано с [Issue #30](https://github.com/zonor922-hub/SurvivalProject/issues/30).
