## Реализация и контракт

Изменён один игровой Blueprint — `/Game/Survival/Inventory/BPC_Inventory`. Поддерживаемым Unreal Blueprint Editor API добавлены:

- **TrySplit(StackId: Guid, Quantity: Integer, TargetSlot: Integer) → FOperationResult**, публичная. Требует 0<Quantity<исходное количество, существующую стопку и конкретный пустой слот в границах массива. Делает копию Slots, сохраняет ID исходной стопки, создаёт новый GUID и копирует ItemId/HasDurability/Durability. Не выбирает другой слот молча и не трактует -1 как автоматический выбор.
- **TryMerge(SourceStackId: Guid, TargetStackId: Guid) → FOperationResult**, публичная. Полностью переносит исходную стопку в принимающую, сохраняет GUID принимающей и оставляет канонический пустой источник. При превышении MaxStack — полный отказ, частичного merge нет. ActualQuantity равен количеству исходной стопки до merge.
- **FindStackIndex(StackId: Guid) → Index: Integer**, private, non-pure. Один ограниченный проход по Slots; отсутствующий ID даёт -1. Non-pure позволяет сохранить найденный индекс и не повторять поиск при каждом чтении выхода. Вызывается только после ValidateSlots.

Обе команды используют существующие ValidateSlots и CommitInventory. Последовательность: проверить готовность/guard/Revision и параметры → захватить guard → проверить текущие слоты и вес → найти стопки/проверить цель → изменить локальную копию → проверить кандидата и сохранение веса → единственный CommitInventory. Реальные Slots не меняются до commit. Commit увеличивает Revision один раз, снимает guard, сохраняет результат и затем вызывает событие.

GUID новой стопки проверяется вместе с кандидатом: случайный нулевой/повторный ID не будет закоммичен. Исходный/принимающий ID остаётся прежним. При merge сравнение количества идёт через `SourceQty <= MaxStack - TargetQty`, после валидации текущих стопок. Сложение выполняется только после этой проверки и не переполняет int32. На Revision=INT32_MAX дальнейшая мутация отклоняется как в A09.

Совместимость merge совпадает с A09: ItemId и HasDurability должны совпасть; активная Durability сравнивается точно. Неактивная Durability не является дискриминатором, но при split её значение копируется. В MVP корректные durable definitions имеют MaxStack=1: разная активная прочность даёт IncompatibleStack, одинаковая всё равно не разрешает объединить две единицы сверх MaxStack. Новая политика durable stacking не вводилась.

### Ошибки и guard

`EOperationError` расширен только в конце, старые номера 0–10 сохранены:

| Номер | Код | Применение |
|---:|---|---|
| 11 | InvalidStackId | Нулевой/неизвестный/исчезнувший GUID либо merge стопки с собой |
| 12 | InvalidSlot | TargetSlot отрицательный или за границами |
| 13 | IncompatibleStack | Разный ItemId, HasDurability или активная Durability |
| 14 | MaxStackExceeded | Полное объединение не помещается в MaxStack |

Повторно используются NotReady=0 (неготовность, повреждение состояния, потолок Revision), InvalidQuantity=6, Busy=7, WeightLimit=8, SlotsFull=9 (занятый целевой слот, в том числе при отсутствии свободных слотов). На отказе ActualQuantity=0, NewRevision равна текущей, Snapshot неизменен, успешных событий нет.

**Busy не сбрасывает уже принадлежащий внешней операции guard.** Иначе вложенная отклонённая команда сняла бы чужую блокировку. Команда освобождает только собственный захват на любом последующем отказе; успешный commit также освобождает его. В тесте Busy владелец снимает свой guard после обеих попыток, что отдельно проверено. Это сохранённая семантика A09.

ChangedSlots — точные два индекса в порядке источник, цель: split 0→1 даёт [0,1]; merge 1→0 даёт [1,0]. Событие только после commit. Из обработчика разрешена новая последовательная команда, а не доступ к промежуточной критической секции. Вложенные multicast callbacks могут приходить разным подписчикам в разном порядке; актуальное состояние читается через GetSnapshot, исходный результат команды сохраняет собственную Revision.

## Стоимость, диагностика и ограничения

В первом полном headless-прогоне 100 пар split/merge на четырёх слотах заняли около 65 ms вместе с Python-вызовами/проверками; точный повторный замер сохранён в metrics. Это локальный образец стоимости, не FPS-обещание и не GPU-бенчмарк. FindStackIndex — ограниченный обход, нет Tick, таймеров, latent/Delay или async внутри команды. Валидация слотов и веса переиспользована; при будущих сотнях слотов стоимость валидатора следует измерить отдельно.

Блокирующих ошибок существующего runtime A09/F02 не найдено. Инфраструктура runner расширена без копирования регрессионных реализаций. Заметка ChangedSlots остаётся прежней и не означает потери массива; ожидаемые ошибки компиляции внешних fixture-Blueprint подтверждают Private-защиту. Процедура анализа не объявляет весь движковый лог свободным от слова Error.

Новая Windows-упаковка и fresh clone с пустым сетевым LFS-кэшем не выполнялись: это не критерии A10, а отдельная интеграционная/доставочная проверка F04. Git LFS 3.8.1: конфигурация required=true сохранена; fsck проходит. Сбой в песочнице был вызван отказом доступа Windows 0xC0000022 при NtCreateDirectoryObject служебного sh.exe MSYS; вне ограниченной среды тот же штатный Git/LFS работает. Фильтры не отключались, реальные ассеты не заменялись указателями. Перед push повторяется fsck и используется обычный pre-push. Сеть, SaveGame и UI инвентаря ещё не реализованы. Ручная визуальная приёмка пользователем не проводилась; данные split/merge проверены автоматически, визуальных изменений A10 не вводит.

## Воспроизведение и проверка пользователем

Редактор этой рабочей копии закрыть. Из корня проекта с UE 5.8.4 и установленным Git/LFS:

```powershell
& './Docs/Architecture/evidence/run_f01_f02.ps1' -EngineRoot 'F:/UE_5.8' -IncludeA10
```

Путь проекта не зашит в скриптах. Результаты — в напечатанном новом Saved/Verification/F01F02/<timestamp>. В summary.json нужны passed=true, process_exit_code=0, timed_out=false, changed_source_files=[]; в a10_pie.json — три успешных runs. -SkipSwimming явно исключает проверку A24 и не используется для полной приёмки.

Когда появится доступ к ПК:

1. Открыть проект ветки A10, затем «Панель ресурсов» → «Содержимое/Survival/Inventory» → BPC_Inventory.
2. В «Моя схема» открыть TrySplit и TryMerge, нажать «Компилировать». Ошибок быть не должно. FindStackIndex должен быть закрытой вспомогательной функцией.
3. Открыть «Содержимое/Survival/Maps» → LV_SystemsTest → «Играть», проверить обычное движение и камеру, затем остановить игру.
4. Для фактического split/merge выполнить команду runner выше: UI инвентаря/клавиш split пока нет. Проверить в a10_pie.json ожидаемые 6+4, merged=10, weight=5, revision=3, events=2 для каждого из трёх запусков. Это повторяемая функциональная проверка; изменения карты для неё не требуются.

## Публикация и A11

PR A10 можно рекомендовать к слиянию после обычного review: обязательные проверки зелёные. Автоматический merge не выполняется. До push проверяются полный исходящий диапазон, diff, отсутствие checkpoint/чужих файлов и LFS. Runtime публикуется отдельным завершённым коммитом; следующий коммит только документации/доказательств указывает SHA повторно проверенного runtime.

Основа для A11 готова; A11 не начиналась. Transfer потребует проверки двух ExpectedRevision и согласованного commit двух копий без событий до готовности обоих inventories. Нельзя заменить такую транзакцию двумя независимыми TryRemove/TryAdd или двумя существующими commit с промежуточным callback. Следующую ветку создавать после приёмки A10 от актуальной main.
