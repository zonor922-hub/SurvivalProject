## 1. Задача из плана

[Backlog A11](03_IMPLEMENTATION_BACKLOG.md): зависимости A09, A10. Результат — `TryTransferExact` с проверкой двух revisions и единым commit двух копий. Проверка: перенос 3 единиц уменьшает источник и увеличивает приёмник на 3; полный приёмник, устаревшая revision и source=destination не теряют и не дублируют предметы; callbacks не видят промежуточное состояние.

[Архитектура §6](02_GAMEPLAY_ARCHITECTURE.md): `TryTransferExact(Source, Destination, StackId, Quantity, ExpectedRevisions)`; «Exact» — всё или ничего; перенос целого стека сохраняет GUID, частичного — создаёт новый; один StackId не может быть одновременно в двух inventories; порядок команды «проверка → guard → копии → проверка результата → применить все копии → ревизии → снять guard → события»; при ошибке ни один inventory не меняется.

## 3. Архитектурное решение

### 3.1 Где живёт команда

Команда — публичная функция **`BPC_Inventory.TryTransferExact`, вызываемая на источнике**. Отдельный координатор-актор/библиотека потребовал бы публичных setter для Slots/Revision/guard, что нарушает A08/A09 (private-поля и отрицательные access-тесты). Внутри одного класса Blueprint функция может работать со вторым экземпляром того же класса.

**Предусловие T0 (блокирующее, проверяет Sol в UE до реализации):** скомпилировать во временном, несохраняемом дубликате/фикстуре функцию BPC_Inventory, которая читает и пишет private-переменные и вызывает private-функцию у *другого* экземпляра BPC_Inventory, и убедиться, что внешний Blueprint по-прежнему получает ошибку компиляции. Ожидание основано на том, что private в Blueprint ограничивает доступ классом, а не экземпляром, но в UE 5.8.4 это здесь не проверялось. Если T0 не проходит — остановиться и вынести решение пользователю (вариант: friend-подобный private-координатор невозможен в Blueprint, потребуется C++ или изменение модели доступа).

T0 нельзя закрыть рассуждением, документацией или облачной проверкой без редактора: результатом считается только запись фактического compile-результата из локального UnrealEditor 5.8.4 (положительный случай внутри класса и отрицательный из внешнего Blueprint). До этой записи реализация A11 не начинается.

### 3.2 Сигнатура

```
TryTransferExact(
    Destination: BPC_Inventory (object ref),
    StackId: Guid,
    Quantity: int,
    ExpectedSourceRevision: int,
    ExpectedDestinationRevision: int)
  -> Result: FOperationResult        // NewRevision = новая ревизия ИСТОЧНИКА
  -> DestinationNewRevision: int     // новая ревизия приёмника; при отказе — текущая
```

- Source = self. Отдельный параметр Source не нужен и исключает вызов «с чужого» компонента.
- Две ExpectedRevision — обязательные целые, без «пропуска» значением −1 (архитектура требует проверки обеих).
- `FOperationResult` не расширять: это изменение структуры A05 и всех потребителей. Вторая ревизия — отдельный выход. (Решение D4 ниже.)
- `ActualQuantity` = Quantity при успехе, 0 при отказе.

### 3.3 Новые внутренние функции (Private, категория `Inventory|Internal`)

| Функция | Вызывается на | Назначение |
|---|---|---|
| `FindStackIndex(StackId) → Index, Found` | источнике | поиск только среди `HasItem=true` и валидных GUID; нулевой GUID никогда не находит пустой слот. Если A10 уже ввела такой helper — переиспользовать |
| `SimulateTakeStack(StackId, Quantity) → CandidateSlots, ChangedSlots, Taken: FItemStack, WholeStack: bool, Error` | источнике | вычесть из одного конкретного стека; при Quantity=Q слот становится каноническим пустым |
| `SimulateReceiveStack(Stack, PreserveStackId: bool) → CandidateSlots, ChangedSlots, Error` | приёмнике | размещение по правилам TryAddExact (D1); проверка слотов, MaxStack, веса, прочности; GUID по D2 |
| `ApplyCandidate(CandidateSlots) → NewRevision` | обоих | только присвоение Slots и Revision+1; **без** снятия guard и без broadcast |
| `BroadcastChange(Revision, ChangedSlots)` | обоих | только вызов OnInventoryChanged |

Существующий `CommitInventory` сохраняется для A09/A10. Причина отдельного `ApplyCandidate`: текущий `CommitInventory` объединяет запись, снятие guard и broadcast. Два последовательных вызова `CommitInventory` дали бы событие источника в момент, когда приёмник ещё не изменён, — обработчик увидел бы промежуточное состояние (прямое нарушение критерия A11). Если Sol предпочтёт рефакторинг `CommitInventory` в `ApplyCandidate + release + Broadcast`, обязательна полная регрессия A09/A10.

### 3.4 Порядок выполнения

```
Фаза 0 — проверки без мутаций (возврат отказа сразу, guard ещё не тронут)
  1. Source.Initialized, IsValid(Destination), Destination.Initialized         → NotReady
  2. Destination == self                                                       → SameInventory (D3)
  3. Source.CatalogGameInstance == Destination.CatalogGameInstance             → NotReady (D5)
  4. Сохранить исходное состояние блокировок в локальные переменные:
     SrcGuardBefore = Source.MutationInProgress; DstGuardBefore = Destination.MutationInProgress
     Если SrcGuardBefore или DstGuardBefore                                    → Busy
     (немедленный возврат; ни один guard не записывается — чужая блокировка
      остаётся нетронутой, свободный инвентарь остаётся свободным)
  5. Revision != ExpectedSourceRevision или
     Destination.Revision != ExpectedDestinationRevision                       → StaleRevision (D3)
  6. Quantity <= 0                                                             → InvalidQuantity
  7. ValidateSlots(Source.Slots) и ValidateSlots(Destination.Slots)             → NotReady
Фаза 1 — guard (этой командой; до этого шага guard не менялся)
  8. Source.MutationInProgress = true; Destination.MutationInProgress = true
Фаза 2 — симуляция на копиях
  9. FindStackIndex: не найден                                                 → StackNotFound
 10. Quantity > Q стека                                                         → InsufficientItems
 11. SimulateTakeStack → SrcCandidate, SrcChanged, Taken, WholeStack
 12. Destination.SimulateReceiveStack(Taken, WholeStack) → DstCandidate, DstChanged, Error
     (SlotsFull / WeightLimit / InvalidDurability / InvalidItemId)
 13. ValidateSlots(SrcCandidate), Destination.ValidateSlots(DstCandidate)
 14. Межинвентарные инварианты: для каждого ItemId сумма (src+dst) до == после;
     ни один StackId не встречается одновременно в SrcCandidate и DstCandidate
     При любой ошибке шагов 9–14: Source.MutationInProgress = SrcGuardBefore;
     Destination.MutationInProgress = DstGuardBefore; вернуть отказ (обе ревизии текущие)
Фаза 3 — commit (без ветвлений, которые могут прерваться)
 15. SrcRev = ApplyCandidate(SrcCandidate); DstRev = Destination.ApplyCandidate(DstCandidate)
 16. Восстановить guard: Source = SrcGuardBefore; Destination = DstGuardBefore
 17. BroadcastChange(SrcRev, SrcChanged); Destination.BroadcastChange(DstRev, DstChanged)
 18. Вернуть (true, None, Quantity, SrcRev), DstRev — значения сохранены в локальных
     переменных ДО broadcast (вложенные команды обработчиков не должны их подменить)
```

Ключевые правила mutation guard:

- **Busy не трогает ни одну блокировку.** Если хотя бы один инвентарь занят, команда возвращает Busy до любой записи в `MutationInProgress`. Снимать или менять блокировку, поставленную другой (внешней, ещё выполняющейся) операцией, запрещено: это открыло бы её незавершённое состояние для чужих изменений.
- Guard ставится только после того, как оба инвентаря проверены на Busy, иначе один из них мог бы остаться заблокированным этой командой.
- Команда восстанавливает **ровно исходное** состояние guard обоих инвентарей (`SrcGuardBefore`, `DstGuardBefore`), а не записывает безусловное `false`. При прохождении шага 4 оба значения равны `false`, но восстановление из сохранённых значений исключает ошибку, если порядок проверок будет изменён при реализации или ревью.
- Каждая ветка отказа после шага 8 восстанавливает guard обоих инвентарей. Удобнее всего — один локальный `Error` и единая точка выхода «восстановить guard → вернуть отказ». Ветки отказа до шага 8 guard не трогают вовсе.
- Живые `Slots` меняются только на шаге 15. Никаких «Получить (ссылка)»/Set Members по элементам члена `Slots` до commit.
- В критической секции нет Delay, latent-узлов, асинхронной загрузки и обращений к UI.
- Шаг 15 состоит только из присваиваний уже проверенных значений: в Blueprint нет транзакций, поэтому всё, что может завершиться ошибкой (Accessed None, поиск определения, вычисления), должно быть выполнено раньше.

### 3.5 Размещение в приёмнике и GUID

Утверждено (D1, D2):

1. **D1 — размещение.** Как в TryAddExact: сначала совместимые стеки по возрастанию индекса до MaxStack, затем пустые слоты по возрастанию индекса. Совместимость: тот же ItemId, тот же HasDurability, при прочности — равная Durability (для MVP прочные предметы имеют MaxStack=1 и фактически не сливаются).
2. **D2 — GUID.**
   - Частичный перенос (Quantity < Q): источник сохраняет свой StackId; каждый стек, созданный в пустом слоте приёмника, получает `NewGuid`; стеки приёмника, принявшие часть количества, сохраняют свои GUID.
   - Полный перенос (Quantity = Q), при котором по правилу D1 вся стопка помещена в **один пустой слот** без слияния: новый стек приёмника получает исходный StackId, слот источника становится каноническим пустым. Если такой GUID уже есть в приёмнике — это повреждённое состояние, отказ NotReady, а не тихая замена.
   - Полный перенос со слиянием (целиком или частично в существующие стеки): GUID принимающих стопок сохраняются; GUID источника исчезает; если остаток занял пустой слот, этот стек получает `NewGuid`, поскольку в один пустой слот помещена не вся стопка.
   - Поскольку D1 требует сначала заполнять совместимые стеки, наличие места в совместимом стеке приводит к слиянию даже при свободном слоте; сохранение исходного GUID в этом случае не выполняется.
3. После commit исходный StackId либо отсутствует в источнике, либо отсутствует в приёмнике — никогда не в обоих (шаг 14).

**Согласование с [архитектурой §6](02_GAMEPLAY_ARCHITECTURE.md).** Архитектура задаёт три правила: «для merge сохранить GUID принимающего стека», «для split создать новый», «перенос целого стека сохраняет GUID, частичного — создаёт новый», и запрещает один StackId в двух inventories. D2 уточняет их без противоречия:

| Правило архитектуры | Применение в A11 |
|---|---|
| Перенос целого стека сохраняет GUID | выполняется, когда целый стек переходит как один стек (один пустой слот) |
| Merge сохраняет GUID принимающего стека | при переносе с объединением приоритет у этого правила: принимающие стопки сохраняют GUID, исходный GUID исчезает |
| Частичный перенос / split создаёт новый GUID | новые стеки в пустых слотах приёмника получают `NewGuid`; источник при частичном переносе сохраняет свой |
| Один StackId не может быть в двух inventories | проверяется шагом 14 и тестами 2, 3, 25 |

Формулировка «перенос целого стека сохраняет GUID» в архитектуре не оговаривает случай слияния; D2 разрешает этот случай в пользу правила merge. В PR реализации A11 Sol должен внести в §6 `02_GAMEPLAY_ARCHITECTURE.md` эту оговорку (в рамках данного PR изменяется только этот документ).

### 3.6 Вес

- Источник: вес только уменьшается — проверка лимита не нужна, но `ValidateSlots` кандидата обязателен.
- Приёмник: тот же метод и тот же допуск, что и в TryAddExact A09 (уточнить в графе ValidateSlots/SimulateAddExact). Нельзя вводить для переноса отдельное, более строгое сравнение: иначе добавление N предметов пройдёт, а перенос тех же N — нет.
- В тестах сравнивать вес с допуском 1e-5, количества — строго. Для berry (0.1) и plank (0.4) вычисленный вес при другом разбиении стеков отличается в последнем бите (например 6×0.1 ≠ 1×0.1+5×0.1), поэтому `==` по весу ненадёжно.

### 3.7 События

- На успехе: ровно одно событие у источника и ровно одно у приёмника, каждое со своей Revision и своими ChangedSlots (по возрастанию, без повторов). Порядок рассылки: источник, затем приёмник; подписчикам на этот порядок полагаться нельзя.
- Оба события отправляются после записи **обоих** инвентарей: обработчик события источника, читая `Destination.GetSnapshot`, уже видит перенесённые предметы, и наоборот.
- Повторный вход: guard восстановлен до broadcast, поэтому обработчик может вызвать новую команду (как в A09). Следствие: если обработчик события источника изменит приёмник, подписчики приёмника получат событие вложенной команды (R+2) **раньше** события переноса (R+1). Это допустимо и должно быть задокументировано.
- **Контракт потребителя (UI и другие зеркала состояния).** Событие — только сигнал «состояние изменилось». Потребитель хранит `ShownRevision` для каждого инвентаря и при событии:
  1. если `Event.Revision ≤ ShownRevision` — ничего не меняет (устаревшее событие);
  2. иначе читает `GetSnapshot()` и применяет его, только если `Snapshot.Revision > ShownRevision`; новое `ShownRevision = Snapshot.Revision` (а не `Event.Revision`: снимок, прочитанный внутри обработчика, может быть уже новее события).
  Так более старая Revision никогда не перезаписывает показанное более новое состояние. Этот контракт обязателен для UI A16/A18; A11 обязана сделать его проверяемым тестами 30a–30e.
- На отказе: ни одного события ни у одного инвентаря.

## 4. Новые коды ошибок

Нужны: `StackNotFound`, `StaleRevision`, `SameInventory`. A10, по рекомендации предварительного аудита, вероятно добавит StackNotFound и другие. **Утверждено (D3):** новые значения A11 добавляются только после всех значений, внесённых A10; значение, уже добавленное A10 с тем же смыслом (например StackNotFound), переиспользуется, а не дублируется. **Не изменять EOperationError до слияния A10**: `EOperationError.uasset` и `BPC_Inventory.uasset` — бинарные LFS-ресурсы, параллельные изменения в двух ветках не сливаются. Новые значения только добавляются в конец (после последнего значения A10), существующие числа не меняются. Изменение enum требует повторить A05-проверку и обновить таблицу в отчёте.

Если пользователь запретит расширять enum: StaleRevision и SameInventory не имеют корректного существующего аналога; переиспользование (например, Busy) делает отказ неразличимым для UI контейнера (A18). Такое решение должно быть записано явно.

## 6. Тесты

Общая проверка отказа `unchanged2`: export_text снимков **обоих** инвентарей прежний, обе Revision прежние, `Success=false`, ожидаемый код, `ActualQuantity=0`, `NewRevision`/`DestinationNewRevision` равны текущим, `MutationInProgress` каждого инвентаря равен значению до вызова, событий 0 у обоих слушателей. Фикстуры — как в A09: временные функции установки guard/слотов, удаляются в finally, ассеты не сохраняются.

### 6.1 Положительные

1. Источник 10 wood, приёмник пуст, перенос 3: источник 7 (тот же GUID), приёмник 3 (новый GUID), Revision обоих +1, ActualQuantity=3, суммы сохранены.

4. Полный перенос стека 5 wood, требующий заполнения существующего стека и пустого слота (приёмник 18 wood → 20+3): стек 20 сохраняет свой GUID, стек 3 получает новый GUID (≠ исходного), исходный GUID исчез из обоих инвентарей (D2).
4a. Полный перенос при наличии и совместимого неполного стека, и пустого слота, когда всё помещается в совместимый стек: по D1 выполняется слияние, исходный GUID не сохраняется, пустой слот остаётся пустым.
4b. Частичный перенос в приёмник с совместимым неполным стеком (приёмник 15 wood, перенос 3 из 10): приёмник 18 с прежним GUID, новых стеков нет, источник 7 с прежним GUID.

6. Перенос berry/plank, при котором вычисленный вес отличается в последнем бите, на границе лимита — не отвергается.
7. Прочный предмет (тестовое определение как в f02: MaxStack=1, DurabilityMax=100) с Durability 37: в приёмнике та же Durability и HasDurability.
8. Перенос из второго стека, когда в источнике два стека одного ItemId — уменьшается именно указанный StackId.
9. События: у источника и приёмника по одному, ChangedSlots точные по возрастанию; обработчик источника видит в снимке приёмника перенесённые предметы, обработчик приёмника — уменьшенный источник.
10. Двусторонний перенос туда и обратно возвращает количества (GUID частичных частей — новые).
11. Последовательность переносов с актуальными ревизиями: каждая следующая ExpectedRevision = предыдущему результату.

### 6.2 Отрицательные (все через `unchanged2`)

12. Приёмник без свободных слотов и без места в совместимых стеках → SlotsFull.
13. Приёмник превысит вес на одну единицу → WeightLimit.
14. Частично помещается (часть в стек, на остаток нет слота) → SlotsFull, ничего не перенесено.
15. Quantity 0, −1, INT_MIN → InvalidQuantity.
16. Quantity Q+1, INT_MAX → InsufficientItems.
17. Нулевой StackId при наличии пустых слотов → StackNotFound.
18. Неизвестный StackId; StackId, существующий только в приёмнике; StackId, уже удалённый → StackNotFound.
19. ExpectedSourceRevision −1 / +1; ExpectedDestinationRevision −1 / +1 → StaleRevision.
20. Destination == self → SameInventory.
21. Destination = None; не инициализирован; источник не инициализирован → NotReady.
22. Разные CatalogGameInstance → NotReady (или код по D5).
23. Busy (фикстура выставляет guard как «чужую» незавершённую операцию):
    - 23a: guard источника = true, приёмника = false → Busy; после вызова источник **остаётся true** (чужая блокировка не снята), приёмник остаётся false;
    - 23b: guard источника = false, приёмника = true → Busy; источник false, приёмник **остаётся true**;
    - 23c: оба true → Busy; оба остаются true;
    - 23d: после каждого случая фикстура сама снимает свою блокировку, и повторный перенос с теми же ревизиями проходит успешно — доказательство, что отказ Busy не изменил ни данных, ни ревизий.
24. Повреждённое состояние источника и приёмника (нулевой/повторный GUID, Q>MaxStack, неверный индекс, неверный HasDurability) → NotReady.
25. Приёмник уже содержит стек с тем же GUID, что переносимый (фикстура) → отказ, дублирования нет.
26. Прочный предмет в приёмник без пустого слота (MaxStack=1) → SlotsFull.

### 6.3 Атомарность и повторный вход

27. Обработчик события источника вызывает TryRemoveExact на приёмнике: внешний результат хранит свои ревизии, итоговые количества = модель, guard обоих равен исходному (false).
28. Обработчик вызывает обратный TryTransferExact с актуальными ревизиями — успешно; с ревизиями, переданными до внешней команды, — StaleRevision.
29. Два подписчика на каждом инвентаре: каждый получает ровно по одному событию переноса.
30. Порядок событий при вложенной команде фиксируется в результатах, но тест не требует конкретного порядка — только полноту и Revision каждого события.

Для 30a–30e используется несохраняемый Blueprint-слушатель `UiMirror` (расширение `inventory_event_fixture.py`), который реализует контракт потребителя 3.7: хранит `ShownRevision`, `ShownSnapshotText`, журнал `(Event.Revision, Snapshot.Revision, Applied)` и счётчик `IgnoredStale`. Отдельно используется «наивный» слушатель, который записывает каждое событие, — только для доказательства, что сценарий действительно доставляет события в обратном порядке.

30a. **Обратный порядок.** UiMirror подписан на приёмник; обработчик источника (Reenter) вызывает TryRemoveExact на приёмнике. Ожидание: наивный слушатель приёмника зафиксировал Revision R+2 раньше R+1; UiMirror по итогам: `ShownRevision = R+2 = Destination.Revision`, `ShownSnapshotText` = текущий `GetSnapshot().export_text()`, событие R+1 записано как `Applied=false`, `IgnoredStale ≥ 1`.
30b. **Монотонность.** Во всём журнале UiMirror применённые `Snapshot.Revision` строго возрастают; ни одна запись с `Applied=true` не имеет Revision меньше предыдущей применённой.
30c. **Снимок новее события.** Если внутри обработчика `Snapshot.Revision > Event.Revision`, UiMirror сохраняет `ShownRevision = Snapshot.Revision`, а последующее событие с промежуточной Revision игнорируется.
30d. **Оба инвентаря.** UiMirror на источнике и на приёмнике одновременно, вложенные команды в обе стороны: итоговые `ShownSnapshotText` обоих равны их текущим `GetSnapshot`.
30e. **Отказ.** Отказ переноса (например StaleRevision) не порождает событий, и UiMirror сохраняет прежние `ShownRevision` и `ShownSnapshotText`.

### 6.4 Модель

31. Расширить модель A09 до двух инвентарей: не менее 600 случайных операций add/remove/transfer (включая stale, Quantity из {−1,0,1,2,9,20,21,INT_MAX}, неизвестные StackId, self-transfer) для трёх пар вместимостей. ## 9. Критерии приёмки A11

- Все тесты раздела 6 проходят; модель — 0 расхождений; регрессия A05–A10/F01/F02/A24 зелёная на чистом коммите, проверка намеренного отказа runner даёт exit=1.

- Callbacks обоих инвентарей не видят промежуточного состояния (тест 9).
- Private-поля и новые внутренние функции недоступны извне (отрицательные compile-тесты).
- Изменены только BPC_Inventory (и EOperationError по D3), тестовые скрипты и документация.
- ProjectStatus и отчёт A11 содержат SHA, проверки, результаты и ограничения.
