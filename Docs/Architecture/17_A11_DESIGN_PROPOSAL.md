## 3. Архитектурное решение

### 3.1 Где живёт команда

Команда — публичная функция **`BPC_Inventory.TryTransferExact`, вызываемая на источнике**. Отдельный координатор-актор/библиотека потребовал бы публичных setter для Slots/Revision/guard, что нарушает A08/A09 (private-поля и отрицательные access-тесты). Внутри одного класса Blueprint функция может работать со вторым экземпляром того же класса.

**Предусловие T0 (блокирующее, проверяет Sol в UE до реализации):** скомпилировать во временном, несохраняемом дубликате/фикстуре функцию BPC_Inventory, которая читает и пишет private-переменные и вызывает private-функцию у *другого* экземпляра BPC_Inventory, и убедиться, что внешний Blueprint по-прежнему получает ошибку компиляции. Ожидание основано на том, что private в Blueprint ограничивает доступ классом, а не экземпляром, но в UE 5.8.4 это здесь не проверялось. Если T0 не проходит — остановиться и вынести решение пользователю (вариант: friend-подобный private-координатор невозможен в Blueprint, потребуется C++ или изменение модели доступа).

T0 нельзя закрыть рассуждением, документацией или облачной проверкой без редактора: результатом считается только запись фактического compile-результата из локального UnrealEditor 5.8.4 (положительный случай внутри класса и отрицательный из внешнего Blueprint). До этой записи реализация A11 не начинается.

### 3.2 Сигнатура

```
TryTransferExact(
    Destination: BPC_Inventory (object ref),
    StackId: Guid,
    Quantity: int,
    ExpectedSourceRevision: int,
    ExpectedDestinationRevision: int)
  -> Result: FOperationResult        // NewRevision = новая ревизия ИСТОЧНИКА
  -> DestinationNewRevision: int     // новая ревизия приёмника; при отказе — текущая;
                                     // −1, если Destination недействителен (None/уничтожается)
```

- Source = self. Отдельный параметр Source не нужен и исключает вызов «с чужого» компонента. Это уточнение сигнатуры `TryTransferExact(Source, Destination, StackId, Quantity, ExpectedRevisions)` из архитектуры §6 внесено туда же отдельной оговоркой.
- TargetSlot отсутствует (D8): размещение в приёмнике только автоматическое по D1; адресное размещение — будущее расширение, не входит в A11.
- Две ExpectedRevision — обязательные целые, без «пропуска» значением −1 (архитектура требует проверки обеих): −1 во входе — обычная несовпадающая ревизия → StaleRevision (тест 19). Значение −1 в выходе DestinationNewRevision означает только недействительный приёмник.
- `FOperationResult` не расширять: это изменение структуры A05 и всех потребителей. Вторая ревизия — отдельный выход. (Решение D4 ниже.)
- `ActualQuantity` = Quantity при успехе, 0 при отказе.
- `DestinationNewRevision`: при успехе — новая ревизия приёмника (сохранена в локальной переменной до событий, шаг 20); при отказе с действительным приёмником — его текущая Revision; при `IsValid(Destination) = false` (None или компонент в процессе уничтожения) — **−1**. Значение −1 никогда не является действительной ревизией: A08 начинает Revision с 0, команды только увеличивают её. На этом пути ни одно поле Destination не читается, поэтому Accessed None невозможен (тест 21). Это единственный новый выход, другие контракты выходов не меняются: `Result.NewRevision` по-прежнему равна текущей ревизии источника.

### 3.3 Новые внутренние функции (Private, категория `Inventory|Internal`)

| Функция | Вызывается на | Назначение |
|---|---|---|
| `FindStackIndex(StackId) → Index` — **существующий helper A10, не создаётся заново** | источнике | переиспользуется без изменения сигнатуры: private, non-pure, −1 при отсутствии стопки; вызывается только после ValidateSlots (шаг 10 ниже). Индекс сохраняется в локальную переменную, поиск не повторяется. Нулевой GUID не находит пустой слот (проверено тестами A10 InvalidStackId) |
| `SimulateTakeStack(Index, Quantity) → CandidateSlots, ChangedSlots, Taken: FItemStack, WholeStack: bool` | источнике | **новая минимальная функция**: у A09/A10 нет вычитания из конкретной стопки (SimulateRemoveExact списывает по ItemId из любых стопок и нарушил бы тест 8; логика TrySplit встроена в её граф). Работает на копии Slots по индексу из FindStackIndex: при Quantity<Q уменьшает Quantity, при Quantity=Q записывает канонический пустой слот так же, как A09/A10 (HasItem=false, нулевой StackId). `Taken` копирует ItemId, HasDurability и Durability (в том числе неактивную) из исходной стопки, как TrySplit A10, Quantity=Quantity, StackId — исходный. Не проверяет вес и не создаёт GUID |
| `SimulateReceiveStack(Taken, WholeStack) → CandidateSlots, ChangedSlots, Error` | приёмнике | **тонкая обёртка над существующим `SimulateAddExact` A09, без собственного алгоритма размещения**: (1) вызывает `SimulateAddExact(Taken)` — совместимость, порядок D1, MaxStack, свободные слоты и новые GUID ровно как в TryAddExact; (2) классификация отказа (SlotsFull / WeightLimit / InvalidDurability / InvalidItemId и их взаимный приоритет) берётся из тех же узлов, что в TryAddExact. Если в A09 эта классификация находится в графе TryAddExact, а не в SimulateAddExact, и её нельзя получить без изменения графа A09 — реализация останавливается и решение выносится пользователю: изменять A09/A10 в рамках A11 без отдельного согласования нельзя, копировать узлы TryAddExact в новую функцию тоже нельзя; (3) единственная добавка — правило D2: если WholeStack и ChangedSlots кандидата состоит ровно из одного слота, пустого в Destination.Slots до операции, в этом слоте кандидата StackId заменяется на `Taken.StackId`. Сравнительный тест 36 доказывает совпадение с TryAddExact |
| `ApplyCandidate(CandidateSlots) → NewRevision` | обоих | только присвоение Slots и Revision+1; **без** снятия guard и без broadcast. Предусловие: Revision < INT32_MAX проверен в фазе 0 (шаг 6) для обоих инвентарей, поэтому сложение не переполняется |
| `BroadcastChange(Revision, ChangedSlots)` | обоих | только вызов OnInventoryChanged |

Повторное использование A09/A10: `ValidateSlots`, `SimulateAddExact`, `FindStackIndex`, канонический пустой слот, правила совместимости и допуск веса — существующие; новые функции не содержат собственных циклов размещения и проверок MaxStack. Вес сравнивается тем же выражением, что в A09/A10 (`Weight ≤ MaxWeight + 1e-5`); единственное новое правило веса — неувеличение веса перегруженного источника (раздел 3.6). Графы TryAddExact, TryRemoveExact, TrySplit, TryMerge, SimulateAddExact, ValidateSlots, FindStackIndex и CommitInventory в A11 не изменяются.

Дополнительная private-функция `CheckTransferInvariants(SrcBefore, DstBefore, SrcCandidate, DstCandidate, Taken) → Ok` содержит циклы шага 16; она только читает аргументы, не пишет поля компонента и не вызывает ApplyCandidate/BroadcastChange/CommitInventory. Вынесение циклов в отдельную функцию оставляет граф TryTransferExact без циклов и делает его пригодным для обхода (тест 33a). Существующий `CommitInventory` сохраняется для A09/A10. Причина отдельного `ApplyCandidate`: текущий `CommitInventory` объединяет запись, снятие guard и broadcast. Два последовательных вызова `CommitInventory` дали бы событие источника в момент, когда приёмник ещё не изменён, — обработчик увидел бы промежуточное состояние (прямое нарушение критерия A11). Рефакторинг `CommitInventory` допускается только по отдельному согласованию пользователя и с полной регрессией A09/A10.

  2. Destination == self                                                       → SameInventory (D3)
  3. Source.InventoryId == Destination.InventoryId (разные объекты)            → NotReady
     (повреждённое состояние: скопированный компонент, аналог A36 DuplicateInventoryId)

     Если SrcGuardBefore или DstGuardBefore                                    → Busy

#### 3.4.1 Агрегаты количества (Integer64)

`Quantity` отдельной стопки остаётся Integer (int32) — тип A05 не меняется. Любая **сумма** нескольких Quantity (шаг 16a, модель, тестовые проверки сохранения) считается в Integer64: каждое значение преобразуется в Integer64 до сложения, сложение int32 + int32 в агрегатах запрещено (в Blueprint оно молча переполняется). Граница: в каждом инвентаре не больше 2³¹−1 слотов, в каждом слоте не больше 2³¹−1 единиц, поэтому сумма по двум инвентарям меньше 2³² · 2³¹ = 2⁶³ и в Integer64 не переполняется. Дополнительно CheckTransferInvariants проверяет, что каждая частичная сумма неотрицательна; отрицательная сумма означает переполнение или повреждение и даёт NotReady. Единственная int32-арифметика количества вне агрегатов — `Q − Quantity` в SimulateTakeStack (не переполняется при 0 < Quantity ≤ Q) и сравнение через вычитание в SimulateAddExact A09. Тесты 39a–39c.

#### Приоритет ошибок

При нескольких нарушениях возвращается код **первой** сработавшей проверки в порядке шагов 1–16. Порядок согласован с A10 («готовность/guard/Revision и параметры → захват guard → текущие слоты и вес → поиск стопки → кандидат»): сначала проверки готовности и целостности пары, затем Busy, затем предел и актуальность ревизий, затем параметры, и только под guard — проверки содержимого. Проверки содержимого (шаги 10–16) выполняются после guard, как в A10, чтобы ни один их путь не обходил восстановление guard. Приоритет закрепляется комбинированными тестами 37.

Ключевые правила mutation guard:

- **Busy не трогает ни одну блокировку.** Если хотя бы один инвентарь занят, команда возвращает Busy до любой записи в `MutationInProgress`. Снимать или менять блокировку, поставленную другой (внешней, ещё выполняющейся) операцией, запрещено: это открыло бы её незавершённое состояние для чужих изменений.
- Guard ставится только после того, как оба инвентаря проверены на Busy, иначе один из них мог бы остаться заблокированным этой командой.
- Команда восстанавливает **ровно исходное** состояние guard обоих инвентарей присваиванием из локальных `SrcGuardBefore` (для источника) и `DstGuardBefore` (для приёмника), а не записывает безусловное `false`; это же требование проверяет обход графа (33a). При прохождении шага 5 оба значения равны `false`, но восстановление из сохранённых значений исключает ошибку, если порядок проверок будет изменён при реализации или ревью.
- Каждая ветка отказа после шага 9 восстанавливает guard обоих инвентарей. Удобнее всего — один локальный `Error` и единая точка выхода «восстановить guard → вернуть отказ». Ветки отказа до шага 9 guard не трогают вовсе.
- Это правило подтверждается не только негативными тестами, но и обязательным автоматическим обходом графа (тест 33a, по образцу A10-M2): ни одна ветка, пропущенная тестами, не должна оставлять guard захваченным.
- Живые `Slots` меняются только на шаге 17. Никаких «Получить (ссылка)»/Set Members по элементам члена `Slots` до commit.
- В критической секции нет Delay, latent-узлов, асинхронной загрузки и обращений к UI.
- Шаг 17 состоит только из присваиваний уже проверенных значений: в Blueprint нет транзакций, поэтому всё, что может завершиться ошибкой (Accessed None, поиск определения, вычисления), должно быть выполнено раньше.

### 3.5 Размещение в приёмнике и GUID

Утверждено (D1, D2, D8):

1. **D1 — размещение.** Как в TryAddExact: сначала совместимые стеки по возрастанию индекса до MaxStack, затем пустые слоты по возрастанию индекса; реализуется вызовом `SimulateAddExact` A09, а не собственным алгоритмом. Соблюдаются MaxStack, лимит веса и число слотов приёмника; если переносимое количество не помещается полностью — отказ без изменения обоих инвентарей (Exact). Совместимость как в A09/A10: тот же ItemId, тот же HasDurability, при HasDurability — точно равная Durability; неактивная Durability не дискриминатор (для MVP прочные предметы имеют MaxStack=1 и фактически не сливаются).
2. **D2 — GUID.**
   - Частичный перенос (Quantity < Q): источник сохраняет свой StackId; каждый стек, созданный в пустом слоте приёмника, получает `NewGuid`; стеки приёмника, принявшие часть количества, сохраняют свои GUID.
   - Полный перенос (Quantity = Q), при котором по правилу D1 вся стопка помещена в **один пустой слот** без слияния: новый стек приёмника получает исходный StackId, слот источника становится каноническим пустым. Если такой GUID уже есть в приёмнике — это повреждённое состояние, отказ NotReady, а не тихая замена.
   - Полный перенос со слиянием (целиком или частично в существующие стеки): GUID принимающих стопок сохраняются; GUID источника исчезает; если остаток занял пустой слот, этот стек получает `NewGuid`, поскольку в один пустой слот помещена не вся стопка.
   - Поскольку D1 требует сначала заполнять совместимые стеки, наличие места в совместимом стеке приводит к слиянию даже при свободном слоте; сохранение исходного GUID в этом случае не выполняется.
3. **D8 — без TargetSlot.** Вызывающий не выбирает слот приёмника; адресное размещение (перетаскивание в конкретную ячейку UI) — будущее расширение отдельной задачей, не A11.
4. После commit исходный StackId либо отсутствует в источнике, либо отсутствует в приёмнике — никогда не в обоих (шаг 16c).
5. **Durability.** Прочность переходит вместе с предметом без изменений: HasDurability и Durability копируются в `Taken` как в TrySplit A10; новые стеки приёмника получают их из `Taken`; принимающие стеки сохраняют свои. Для предметов с HasDurability=true значение Durability — свойство предмета и входит в ключ сохранения (16a). Для HasDurability=false значение Durability неактивно: оно не входит в ключ сохранения и не является дискриминатором слияния (A09/A10); для единообразия с TrySplit оно копируется в новый стек приёмника, а при слиянии теряется вместе с исчезающим исходным стеком — это не считается изменением предмета. Шаг 16a/16b проверяет это до commit, тесты 7–7c и 40 — на всех путях.

**Согласование с [архитектурой §6](02_GAMEPLAY_ARCHITECTURE.md).** Архитектура задаёт три правила: «для merge сохранить GUID принимающего стека», «для split создать новый», «перенос целого стека сохраняет GUID, частичного — создаёт новый», и запрещает один StackId в двух inventories. D2 уточняет их без противоречия:

| Правило архитектуры | Применение в A11 |
|---|---|
| Перенос целого стека сохраняет GUID | выполняется, когда целый стек переходит как один стек (один пустой слот) |
| Merge сохраняет GUID принимающего стека | при переносе с объединением приоритет у этого правила: принимающие стопки сохраняют GUID, исходный GUID исчезает |
| Частичный перенос / split создаёт новый GUID | новые стеки в пустых слотах приёмника получают `NewGuid`; источник при частичном переносе сохраняет свой |
| Один StackId не может быть в двух inventories | проверяется шагом 16c и тестами 2, 3, 25 |

Формулировка «перенос целого стека сохраняет GUID» в архитектуре не оговаривала случай слияния; D2 разрешает этот случай в пользу правила merge. Оговорка D2 внесена в этом же PR в оба документа, где правило записано: §6 [`02_GAMEPLAY_ARCHITECTURE.md`](02_GAMEPLAY_ARCHITECTURE.md) и §6.3 [`15_A36_SAVEGAME_ARCHITECTURE.md`](15_A36_SAVEGAME_ARCHITECTURE.md). Проверка A36 T15 (`DuplicateStackId` между инвентарями) от этого не меняется. PR реализации A11 должен сверить фактическое поведение с этой оговоркой и описать расхождения, если они появятся.

### 3.6 Вес

- Сравнение с лимитом — то же выражение, что в A09/A10: `Weight ≤ MaxWeight + 1e-5`, вес берётся из ValidateSlots. Отдельной формулы суммирования веса в A11 нет.
- **Приёмник** не может превысить лимит: `DstWeightAfter ≤ Destination.MaxWeight + 1e-5`, иначе WeightLimit (шаг 15). Если приёмник уже перегружен до переноса, отказ WeightLimit выдаётся на шаге 10 — как «overweight state» в A10, даже для предмета с UnitWeight = 0. Условия приёмника не строже, чем у добавления: если `TryAddExact(Taken)` в копию приёмника проходит, перенос того же Taken тоже проходит по условиям приёмника (тест 36). Отказ переноса по причинам источника (стопка, количество, ревизия) этим правилом не затрагивается.
- **Источник** (решение N1 аудита): перенос **из** перегруженного источника разрешён, если вес источника не увеличивается. Кандидат источника проходит, если `SrcWeightAfter ≤ MaxWeight + 1e-5` **или** `SrcWeightAfter ≤ SrcWeightBefore + 1e-5`. Так как перенос только вычитает, второе условие выполняется всегда; проверка оставлена как инвариант против ошибки реализации. Следствия:
  - последовательная разгрузка разрешена: после первого переноса источник может остаться перегруженным, следующий перенос с новыми ревизиями снова разрешён;
  - выход ровно на лимит и ниже лимита — обычный успех;
  - перегруз источника до переноса не является отказом (в отличие от A10, где перегруз инвентаря блокирует split/merge — это поведение A09/A10 не меняется: TryAddExact, TrySplit, TryMerge на перегруженном инвентаре по-прежнему возвращают WeightLimit).
- Почему не прежний вариант «перегруз любого инвентаря → WeightLimit»: перегруз возникает без участия игрока (смена профиля или MaxWeight, загрузка сохранения со старым балансом); запрет переноса оставил бы такой инвентарь заблокированным навсегда, потому что выгрузить предметы можно только переносом или удалением.
- В тестах вес сравнивается с допуском 1e-5, количества — строго. Для berry (0.1) и plank (0.4) вычисленный вес при другом разбиении стеков отличается в последнем бите (например 6×0.1 ≠ 1×0.1+5×0.1), поэтому `==` по весу ненадёжно. Нормативные границы приёмника: превышение на 1e-6 — успех, на 1e-3 — WeightLimit (как A10-M2).

### 3.7 События

- На успехе: ровно одно событие у источника и ровно одно у приёмника (единственное исключение — приёмник уничтожен обработчиком источника, см. ниже и путь P4 теста 33a), каждое со своей Revision и своими ChangedSlots (по возрастанию, без повторов). Порядок рассылки в команде: источник, затем приёмник. Подписчики не должны строить логику на порядке событий между инвентарями и между вложенными командами — только на контракте потребителя ниже; тесты фиксируют фактический порядок лишь как диагностику и для доказательства сценария 30a.
- Оба события отправляются после записи **обоих** инвентарей: обработчик события источника, читая `Destination.GetSnapshot`, уже видит перенесённые предметы, и наоборот.
- Повторный вход: guard восстановлен до broadcast, поэтому обработчик может вызвать новую команду (как в A09). Следствие: если обработчик события источника изменит приёмник, подписчики приёмника получат событие вложенной команды (R+2) **раньше** события переноса (R+1). Это допустимо и должно быть задокументировано.
- **Контракт потребителя (UI и другие зеркала состояния).** Событие — только сигнал «состояние изменилось». Потребитель хранит `ShownRevision` для каждого инвентаря и при событии:
  1. если `Event.Revision ≤ ShownRevision` — ничего не меняет (устаревшее событие);
  2. иначе читает `GetSnapshot()` и применяет его, только если `Snapshot.Revision > ShownRevision`; новое `ShownRevision = Snapshot.Revision` (а не `Event.Revision`: снимок, прочитанный внутри обработчика, может быть уже новее события).
  Так более старая Revision никогда не перезаписывает показанное более новое состояние. Этот контракт обязателен для UI A16/A18; A11 обязана сделать его проверяемым тестами 30a–30e.
- Если обработчик события источника уничтожил приёмник, событие приёмника не рассылается (шаг 19): компонент уничтожается, его подписчики больше не должны отображать его состояние. Результат команды остаётся успешным — запись обоих инвентарей уже выполнена; `DestinationNewRevision` = DstRev из локальной переменной. Это единственный допустимый успешный путь с одним событием; обход графа (33a) перечисляет его отдельно. Перенос, при котором предметы записаны в уничтожаемый приёмник, — сценарий A18/A19 (контейнер обязан закрывать UI и не принимать команды при уничтожении); A11 не теряет данные сверх этого: состояние приёмника записано до уничтожения.
- На отказе: ни одного события ни у одного инвентаря.

### 3.8 Согласованность с A36 и A39

[A36](15_A36_SAVEGAME_ARCHITECTURE.md) — принятый проект схемы сохранения; A39 — будущая задача восстановления. A11 не меняет DTO и не вызывает сохранение. Контракты, на которые A11 опирается или которые она обязана соблюдать:

| Контракт A36/A39 | Поведение A11 |

| §4.2 п. 1: запрос сохранения отклоняется, пока активен mutation guard любого inventory | Guard обоих инвентарей держится от шага 9 до шага 18; сохранение, запрошенное из обработчика события (шаг 19), видит оба инвентаря уже записанными — промежуточного состояния в DTO быть не может |
| §5.3 `FSave_ItemStack` {StackId, ItemId, Quantity, HasDurability, Durability} | Перенос меняет только эти поля существующими правилами; новых полей и состояний нет, схема v1 не меняется |
| §6.3 StackId уникален во **всех** inventories сохранения | Шаг 16c проверяет пару участников; сохранение исходного GUID при целом переносе не создаёт дубликата, так как GUID покидает источник. Уникальность относительно остальных inventories опирается на инвариант A36 (T15) и на `NewGuid` для новых стопок |
| §6.4 InventoryId уникален | Шаг 3 отклоняет пару разных компонентов с одинаковым InventoryId |
| §6.4 после восстановления Revision = сохранённая + 1 | **Не гарантирует** отклонения всех команд, созданных до загрузки (контрпример 10→11 ниже). Шаг 7 A11 отклоняет только ревизии, не равные текущей; гарантированное инвалидирование прежних команд — требование к A39 (ниже, тест 38) |
| §6.4 предел ревизии | Шаг 6 не допускает переполнения при переносе. Восстановление сохранения с Revision = INT32_MAX («+1» невозможно) — ответственность A39 |
| §10.2 п. 7 `Summary`: сумма Quantity по ItemId | Шаг 16a сохраняет суммы по двум инвентарям строго, поэтому сводка сохранения не меняется от переноса. Тип поля суммы в `FSave_Summary` A36 не задан; так как сумма по всем inventories может превысить INT32_MAX (3.4.1), реализации A36 рекомендуется Integer64 — это записано как риск K23, формат A36 здесь не меняется |
| §6.4 / A39: `RestoreFromSave` разрешён только до Ready | Перенос требует Initialized обоих (шаг 1) и не вызывается в фазе Restore; A39 должна не допускать команд inventory до Activate |

**Контрпример к «сохранённая + 1» (N2).** Инвентарь сохранён при Revision = 10. После сохранения игрок выполняет ещё одну команду: живая Revision = 11. UI или контейнер запоминает ExpectedRevision = 11 и держит подготовленную команду (например открытое окно переноса). Затем игрок загружает сохранение: восстановлено состояние ревизии 10, A39 выставляет Revision = 10 + 1 = **11**. Подготовленная до загрузки команда с ExpectedRevision = 11 совпадает с новой ревизией и проходит шаг 7, хотя относится к другому состоянию (после загрузки предметов, которые она видела, может не быть). Правило «+1» отклоняет любую ревизию, кроме «сохранённая + 1»; ложно проходит именно команда, полученная после сохранения, когда живая ревизия была ровно «сохранённая + 1» (одна команда после сохранения — частый случай).

**Требование к A39 (передаётся, в A11 не реализуется).** A39 обязана гарантированно инвалидировать все команды и привязки, полученные до загрузки, независимо от совпадения номеров ревизий. Допустимые варианты (выбор — в A39 с отдельным согласованием):

1. **Инвалидирование привязок при загрузке.** Загрузка закрывает все окна инвентаря и контейнеров, отменяет подготовленные команды, отписывает слушателей и заново получает ссылки и snapshot после фазы Activate; новые ExpectedRevision берутся только из нового snapshot. Формат сохранения не меняется.
2. **Эпоха команд.** Runtime-счётчик (например LoadEpoch в GameInstance, не сохраняется), который увеличивается при каждой загрузке; команда несёт эпоху, полученную вместе с ревизией, и отклоняется при несовпадении. Это изменение публичной сигнатуры команд inventory (A09/A10/A11) и требует отдельного решения; формат A36 не меняется.
3. **Ревизия выше любой ранее выданной.** Например Revision = max(сохранённая, последняя живая) + 1 — требует знать живую ревизию на момент загрузки и не работает после перезапуска приложения; рассматривается только вместе с вариантом 1.

A11 не выбирает вариант и не меняет архитектуру A36. Тест 38 (в A39) проверяет именно контрпример.

Соответствующие уточнения внесены в A36 (§6.3, §6.4, T49 и таблицу состояния задач).

| Хотя бы одна ExpectedRevision не совпадает | `StaleRevision` = 15 | новый, A11 |
| Destination == Source | `SameInventory` = 16 | новый, A11 |

Номера 15 и 16 — следующие свободные после A10; окончательные значения подтверждаются при изменении enum в PR реализации повторной A05-проверкой. `SameInventory` отделён от `InvalidStackId` (которым A10 отклоняет merge стопки с собой), потому что при переносе StackId корректен, ошибочен выбор инвентаря. `EOperationError.uasset` и `BPC_Inventory.uasset` — бинарные LFS-ресурсы: менять их только в ветке реализации от актуальной main. Новые значения только добавляются в конец, существующие числа не меняются. Изменение enum требует повторить A05-проверку и обновить таблицу в отчёте.

Если пользователь запретит расширять enum: StaleRevision и SameInventory не имеют корректного существующего аналога; переиспользование (например, Busy) делает отказ неразличимым для UI контейнера (A18). Такое решение должно быть записано явно.

### 6.3 Атомарность и повторный вход

27. Обработчик события источника вызывает TryRemoveExact на приёмнике: внешний результат хранит свои ревизии, итоговые количества = модель, guard обоих равен исходному (false).
28. Обработчик вызывает обратный TryTransferExact с актуальными ревизиями — успешно; с ревизиями, переданными до внешней команды, — StaleRevision.
29. Два подписчика на каждом инвентаре: каждый получает ровно по одному событию переноса.
29a. Обработчик события источника уничтожает компонент приёмника: результат переноса успешен, `DestinationNewRevision` = ревизия приёмника после записи, в журнале нет Accessed None, у источника ровно одно событие, событие уничтоженного приёмника не рассылается.
30. Порядок событий при вложенной команде записывается в результаты как диагностика. Критерии PASS тестов 27–29 не зависят от порядка: только полнота событий и Revision каждого. Единственное исключение — 30a, где обратный порядок является предпосылкой сценария и проверяется наивным слушателем, чтобы доказать, что UiMirror действительно получил устаревшее событие.

Для 30a–30e используется несохраняемый Blueprint-слушатель `UiMirror` (расширение `inventory_event_fixture.py`), который реализует контракт потребителя 3.7: хранит `ShownRevision`, `ShownSnapshotText`, журнал `(Event.Revision, Snapshot.Revision, Applied)` и счётчик `IgnoredStale`. Отдельно используется «наивный» слушатель, который записывает каждое событие, — только для доказательства, что сценарий действительно доставляет события в обратном порядке.

30a. **Обратный порядок.** UiMirror подписан на приёмник; обработчик источника (Reenter) вызывает TryRemoveExact на приёмнике. Ожидание: наивный слушатель приёмника зафиксировал Revision R+2 раньше R+1; UiMirror по итогам: `ShownRevision = R+2 = Destination.Revision`, `ShownSnapshotText` = текущий `GetSnapshot().export_text()`, событие R+1 записано как `Applied=false`, `IgnoredStale ≥ 1`.
30b. **Монотонность.** Во всём журнале UiMirror применённые `Snapshot.Revision` строго возрастают; ни одна запись с `Applied=true` не имеет Revision меньше предыдущей применённой.
30c. **Снимок новее события.** Если внутри обработчика `Snapshot.Revision > Event.Revision`, UiMirror сохраняет `ShownRevision = Snapshot.Revision`, а последующее событие с промежуточной Revision игнорируется.
30d. **Оба инвентаря.** UiMirror на источнике и на приёмнике одновременно, вложенные команды в обе стороны: итоговые `ShownSnapshotText` обоих равны их текущим `GetSnapshot`.
30e. **Отказ.** Отказ переноса (например StaleRevision) не порождает событий, и UiMirror сохраняет прежние `ShownRevision` и `ShownSnapshotText`.

### 6.4 Модель

31. **Модель двух инвентарей** (чистый Python, расширение модели A09, без UE для части 31-M и с UE для части 31-U, где каждая операция выполняется настоящими командами и сравнивается с моделью).
    - **Состояние модели:** слоты, Revision и guard каждого инвентаря; внешний учёт `External[key]` — сколько единиц каждого ключа вошло в систему через Add и вышло через Remove. Ключ — (ItemId, HasDurability, Durability при HasDurability); дополнительно ведётся баланс только по ItemId.
    - **Законы сохранения** (суммы — целые произвольной точности в Python, Integer64 в UE):
      - Transfer успех: Σ по двум инвентарям для каждого ключа не меняется; у источника ключ уменьшается на Quantity, у приёмника увеличивается на Quantity;
      - Add успех: Σ ключа увеличивается ровно на добавленное количество;
      - Remove успех: Σ ItemId уменьшается ровно на удалённое количество, распределение по стопкам и ключам Durability — по модели A09;
      - любой отказ (любой операции): снимки обоих инвентарей побайтно прежние, Revision и guard прежние, событий нет.
    - **Дополнительные инварианты после каждой операции:** состояние = модель; код ошибки = модель (в том числе приоритет 3.4); StackId уникальны в объединении; Revision каждого = число его успешных изменений; вес приёмника ≤ лимита + 1e-5; вес источника после переноса ≤ лимита + 1e-5 или не больше, чем до переноса.
    - **Генерация:** фиксированный seed (базовый 20261027, для пары вместимостей i — 20261027 + i), записывается в evidence. Три пары вместимостей (4/4 слота, 4/1 слот, 8/2 слота; разные MaxWeight, одна пара с перегруженным источником). Не менее 600 операций на пару (1800 всего). Распределение: Transfer 50 %, Add 30 %, Remove 20 %. Внутри Transfer: Quantity из {−1, 0, 1, 2, 9, 20, 21, INT32_MAX}, 20 % неизвестных или нулевых StackId, 5 % self-transfer, 10 % устаревших ревизий, 5 % с guard «чужой» операции; предметы — wood, berry (0.1), прочный (MaxStack=1, Durability из {0, 37, 80, 100}), большой (MaxStack = INT32_MAX, UnitWeight = 0).
    - **Покрытие (провал, если не достигнуто):** ≥ 300 успешных Transfer, ≥ 100 успешных Add и ≥ 50 успешных Remove; каждый код отказа Transfer (NotReady, SameInventory, Busy, StaleRevision, InvalidQuantity, InvalidStackId, InsufficientItems, SlotsFull, WeightLimit) — не менее 5 раз; ≥ 20 успешных переносов из перегруженного источника; ≥ 10 состояний, где Σ Quantity ключа > INT32_MAX. Фактическое число каждого исхода записывается в evidence; при недостижении — FAIL, а не тихий PASS.
