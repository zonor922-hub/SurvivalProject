## 3. Архитектурное решение

### 3.1 Где живёт команда

Команда — публичная функция **`BPC_Inventory.TryTransferExact`, вызываемая на источнике**. Отдельный координатор-актор/библиотека потребовал бы публичных setter для Slots/Revision/guard, что нарушает A08/A09 (private-поля и отрицательные access-тесты). Внутри одного класса Blueprint функция может работать со вторым экземпляром того же класса.

**Предусловие T0 (блокирующее, проверяет Sol в UE до реализации):** скомпилировать во временном, несохраняемом дубликате/фикстуре функцию BPC_Inventory, которая читает и пишет private-переменные и вызывает private-функцию у *другого* экземпляра BPC_Inventory, и убедиться, что внешний Blueprint по-прежнему получает ошибку компиляции. Ожидание основано на том, что private в Blueprint ограничивает доступ классом, а не экземпляром, но в UE 5.8.4 это здесь не проверялось. Если T0 не проходит — остановиться и вынести решение пользователю (вариант: friend-подобный private-координатор невозможен в Blueprint, потребуется C++ или изменение модели доступа).

T0 нельзя закрыть рассуждением, документацией или облачной проверкой без редактора: результатом считается только запись фактического compile-результата из локального UnrealEditor 5.8.4 (положительный случай внутри класса и отрицательный из внешнего Blueprint). До этой записи реализация A11 не начинается.

### 3.2 Сигнатура

```
TryTransferExact(
    Destination: BPC_Inventory (object ref),
    StackId: Guid,
    Quantity: int,
    ExpectedSourceRevision: int,
    ExpectedDestinationRevision: int)
  -> Result: FOperationResult        // NewRevision = новая ревизия ИСТОЧНИКА
  -> DestinationNewRevision: int     // новая ревизия приёмника; при отказе — текущая
```

- Source = self. Отдельный параметр Source не нужен и исключает вызов «с чужого» компонента. Это уточнение сигнатуры `TryTransferExact(Source, Destination, StackId, Quantity, ExpectedRevisions)` из архитектуры §6 внесено туда же отдельной оговоркой.
- TargetSlot отсутствует (D8): размещение в приёмнике только автоматическое по D1; адресное размещение — будущее расширение, не входит в A11.
- Две ExpectedRevision — обязательные целые, без «пропуска» значением −1 (архитектура требует проверки обеих).
- `FOperationResult` не расширять: это изменение структуры A05 и всех потребителей. Вторая ревизия — отдельный выход. (Решение D4 ниже.)
- `ActualQuantity` = Quantity при успехе, 0 при отказе.

### 3.3 Новые внутренние функции (Private, категория `Inventory|Internal`)

| Функция | Вызывается на | Назначение |
|---|---|---|
| `FindStackIndex(StackId) → Index` — **существующий helper A10, не создаётся заново** | источнике | переиспользуется без изменения сигнатуры: private, non-pure, −1 при отсутствии стопки; вызывается только после ValidateSlots (шаг 10 ниже). Индекс сохраняется в локальную переменную, поиск не повторяется. Нулевой GUID не находит пустой слот (проверено тестами A10 InvalidStackId) |
| `SimulateTakeStack(Index, Quantity) → CandidateSlots, ChangedSlots, Taken: FItemStack, WholeStack: bool` | источнике | **новая минимальная функция**: у A09/A10 нет вычитания из конкретной стопки (SimulateRemoveExact списывает по ItemId из любых стопок и нарушил бы тест 8; логика TrySplit встроена в её граф). Работает на копии Slots по индексу из FindStackIndex: при Quantity<Q уменьшает Quantity, при Quantity=Q записывает канонический пустой слот так же, как A09/A10 (HasItem=false, нулевой StackId). `Taken` копирует ItemId, HasDurability и Durability (в том числе неактивную) из исходной стопки, как TrySplit A10, Quantity=Quantity, StackId — исходный. Не проверяет вес и не создаёт GUID |
| `SimulateReceiveStack(Taken, WholeStack) → CandidateSlots, ChangedSlots, Error` | приёмнике | **тонкая обёртка над существующим `SimulateAddExact` A09, без собственного алгоритма размещения**: (1) вызывает `SimulateAddExact(Taken)` — совместимость, порядок D1, MaxStack, свободные слоты и новые GUID ровно как в TryAddExact; (2) классификация отказа (SlotsFull / WeightLimit / InvalidDurability / InvalidItemId и их взаимный приоритет) берётся из тех же узлов, что в TryAddExact. Если в A09 эта классификация находится в графе TryAddExact, а не в SimulateAddExact, её выносят в private helper, общий для TryAddExact и переноса, с полной регрессией A09; копировать узлы в новую функцию запрещено; (3) единственная добавка — правило D2: если WholeStack и ChangedSlots кандидата состоит ровно из одного слота, пустого в Destination.Slots до операции, в этом слоте кандидата StackId заменяется на `Taken.StackId`. Сравнительный тест 36 доказывает совпадение с TryAddExact |
| `ApplyCandidate(CandidateSlots) → NewRevision` | обоих | только присвоение Slots и Revision+1; **без** снятия guard и без broadcast. Предусловие: Revision < INT32_MAX проверен в фазе 0 (шаг 6) для обоих инвентарей, поэтому сложение не переполняется |
| `BroadcastChange(Revision, ChangedSlots)` | обоих | только вызов OnInventoryChanged |

Повторное использование A09/A10: `ValidateSlots`, `SimulateAddExact`, `FindStackIndex`, канонический пустой слот, правила совместимости и допуск веса — существующие; новые функции не содержат собственных циклов размещения, сравнений веса или проверок MaxStack. Существующий `CommitInventory` сохраняется для A09/A10. Причина отдельного `ApplyCandidate`: текущий `CommitInventory` объединяет запись, снятие guard и broadcast. Два последовательных вызова `CommitInventory` дали бы событие источника в момент, когда приёмник ещё не изменён, — обработчик увидел бы промежуточное состояние (прямое нарушение критерия A11). Если Sol предпочтёт рефакторинг `CommitInventory` в `ApplyCandidate + release + Broadcast`, обязательна полная регрессия A09/A10.

### 3.4 Порядок выполнения

```
Фаза 0 — проверки без мутаций (возврат отказа сразу, guard ещё не тронут)
  1. Source.Initialized, IsValid(Destination), Destination.Initialized         → NotReady
  2. Destination == self                                                       → SameInventory (D3)
  3. Source.InventoryId == Destination.InventoryId (разные объекты)            → NotReady
     (повреждённое состояние: скопированный компонент, аналог A36 DuplicateInventoryId)
  4. Source.CatalogGameInstance != Destination.CatalogGameInstance             → NotReady (D5)
  5. Сохранить исходное состояние блокировок в локальные переменные:
     SrcGuardBefore = Source.MutationInProgress; DstGuardBefore = Destination.MutationInProgress
     Если SrcGuardBefore или DstGuardBefore                                    → Busy
     (немедленный возврат; ни один guard не записывается — чужая блокировка
      остаётся нетронутой, свободный инвентарь остаётся свободным)
  6. Revision == INT32_MAX или Destination.Revision == INT32_MAX               → NotReady
     (предел ревизии как в A10; проверяется для ОБОИХ до любой записи, иначе
      источник был бы записан, а Revision+1 приёмника переполнилась бы)
  7. Revision != ExpectedSourceRevision или
     Destination.Revision != ExpectedDestinationRevision                       → StaleRevision (D3)
  8. Quantity <= 0                                                             → InvalidQuantity
Фаза 1 — guard (этой командой; до этого шага guard не менялся)
  9. Source.MutationInProgress = true; Destination.MutationInProgress = true
Фаза 2 — проверки состояния и симуляция на копиях (как в A10: после захвата guard)
 10. ValidateSlots(Source.Slots), Destination.ValidateSlots(Destination.Slots)  → NotReady
     StackId повторяется в объединении текущих слотов обоих инвентарей        → NotReady
     текущий вес любого инвентаря > MaxWeight + 1e-5                           → WeightLimit
     (то же сравнение и тот же код, что «overweight state» в A10)
 11. FindStackIndex (helper A10): −1, в т. ч. нулевой GUID                     → InvalidStackId (11)
 12. Quantity > Q стека                                                        → InsufficientItems
 13. SimulateTakeStack(Index, Quantity) → SrcCandidate, SrcChanged, Taken, WholeStack
 14. Destination.SimulateReceiveStack(Taken, WholeStack) → DstCandidate, DstChanged, Error
     (коды и их приоритет — как TryAddExact для того же Taken)
 15. ValidateSlots(SrcCandidate), Destination.ValidateSlots(DstCandidate)       → NotReady;
     вес кандидата > MaxWeight + 1e-5                                          → WeightLimit
 16. Межинвентарные инварианты (отказ — NotReady, это ошибка реализации):
     a) для каждого ключа (ItemId, HasDurability, Durability при HasDurability) сумма
        Quantity по двум инвентарям до == после;
     b) Taken совпадает с вычтенной частью по ItemId, HasDurability, Durability;
        каждая стопка приёмника, принявшая количество, сохранила свои HasDurability/Durability;
        каждая новая стопка приёмника имеет HasDurability/Durability = Taken;
     c) ни один StackId не встречается одновременно в SrcCandidate и DstCandidate.
     При любой ошибке шагов 10–16: Source.MutationInProgress = SrcGuardBefore;
     Destination.MutationInProgress = DstGuardBefore; вернуть отказ (обе ревизии текущие)
Фаза 3 — commit (без ветвлений, которые могут прерваться)
 17. SrcRev = ApplyCandidate(SrcCandidate); DstRev = Destination.ApplyCandidate(DstCandidate)
 18. Восстановить guard: Source = SrcGuardBefore; Destination = DstGuardBefore
 19. BroadcastChange(SrcRev, SrcChanged);
     если IsValid(Destination): Destination.BroadcastChange(DstRev, DstChanged)
     (обработчик источника мог уничтожить приёмник; состояние уже записано,
      событие уничтожаемого компонента пропускается без Accessed None)
 20. Вернуть (true, None, Quantity, SrcRev), DstRev — значения сохранены в локальных
     переменных ДО broadcast (вложенные команды обработчиков не должны их подменить)
```

#### Приоритет ошибок

При нескольких нарушениях возвращается код **первой** сработавшей проверки в порядке шагов 1–16. Порядок согласован с A10 («готовность/guard/Revision и параметры → захват guard → текущие слоты и вес → поиск стопки → кандидат»): сначала проверки готовности и целостности пары, затем Busy, затем предел и актуальность ревизий, затем параметры, и только под guard — проверки содержимого. Проверки содержимого (шаги 10–16) выполняются после guard, как в A10, чтобы ни один их путь не обходил восстановление guard. Приоритет закрепляется комбинированными тестами 37.

| Приоритет | Шаг | Код |
|---:|---|---|
| 1 | 1 — источник/приёмник не готов, Destination=None | NotReady |
| 2 | 2 — Destination == Source | SameInventory |
| 3 | 3 — одинаковый InventoryId у разных объектов | NotReady |
| 4 | 4 — разные каталоги | NotReady |
| 5 | 5 — guard любого инвентаря | Busy |
| 6 | 6 — Revision = INT32_MAX у любого | NotReady |
| 7 | 7 — ExpectedRevision не совпадает | StaleRevision |
| 8 | 8 — Quantity ≤ 0 | InvalidQuantity |
| 9 | 10 — повреждённые слоты, общий StackId в паре / перегруз текущего состояния | NotReady / WeightLimit |
| 10 | 11 — StackId не найден | InvalidStackId |
| 11 | 12 — Quantity > Q | InsufficientItems |
| 12 | 14 — приёмник не может принять (порядок кодов как в TryAddExact) | SlotsFull / WeightLimit / InvalidDurability / InvalidItemId |
| 13 | 15–16 — кандидат или инварианты | NotReady / WeightLimit |

Ключевые правила mutation guard:

- **Busy не трогает ни одну блокировку.** Если хотя бы один инвентарь занят, команда возвращает Busy до любой записи в `MutationInProgress`. Снимать или менять блокировку, поставленную другой (внешней, ещё выполняющейся) операцией, запрещено: это открыло бы её незавершённое состояние для чужих изменений.
- Guard ставится только после того, как оба инвентаря проверены на Busy, иначе один из них мог бы остаться заблокированным этой командой.
- Команда восстанавливает **ровно исходное** состояние guard обоих инвентарей (`SrcGuardBefore`, `DstGuardBefore`), а не записывает безусловное `false`. При прохождении шага 5 оба значения равны `false`, но восстановление из сохранённых значений исключает ошибку, если порядок проверок будет изменён при реализации или ревью.
- Каждая ветка отказа после шага 9 восстанавливает guard обоих инвентарей. Удобнее всего — один локальный `Error` и единая точка выхода «восстановить guard → вернуть отказ». Ветки отказа до шага 9 guard не трогают вовсе.
- Это правило подтверждается не только негативными тестами, но и обязательным автоматическим обходом графа (тест 33a, по образцу A10-M2): ни одна ветка, пропущенная тестами, не должна оставлять guard захваченным.
- Живые `Slots` меняются только на шаге 17. Никаких «Получить (ссылка)»/Set Members по элементам члена `Slots` до commit.
- В критической секции нет Delay, latent-узлов, асинхронной загрузки и обращений к UI.
- Шаг 17 состоит только из присваиваний уже проверенных значений: в Blueprint нет транзакций, поэтому всё, что может завершиться ошибкой (Accessed None, поиск определения, вычисления), должно быть выполнено раньше.

### 3.5 Размещение в приёмнике и GUID

Утверждено (D1, D2, D8):

1. **D1 — размещение.** Как в TryAddExact: сначала совместимые стеки по возрастанию индекса до MaxStack, затем пустые слоты по возрастанию индекса; реализуется вызовом `SimulateAddExact` A09, а не собственным алгоритмом. Соблюдаются MaxStack, лимит веса и число слотов приёмника; если переносимое количество не помещается полностью — отказ без изменения обоих инвентарей (Exact). Совместимость как в A09/A10: тот же ItemId, тот же HasDurability, при HasDurability — точно равная Durability; неактивная Durability не дискриминатор (для MVP прочные предметы имеют MaxStack=1 и фактически не сливаются).
2. **D2 — GUID.**
   - Частичный перенос (Quantity < Q): источник сохраняет свой StackId; каждый стек, созданный в пустом слоте приёмника, получает `NewGuid`; стеки приёмника, принявшие часть количества, сохраняют свои GUID.
   - Полный перенос (Quantity = Q), при котором по правилу D1 вся стопка помещена в **один пустой слот** без слияния: новый стек приёмника получает исходный StackId, слот источника становится каноническим пустым. Если такой GUID уже есть в приёмнике — это повреждённое состояние, отказ NotReady, а не тихая замена.
   - Полный перенос со слиянием (целиком или частично в существующие стеки): GUID принимающих стопок сохраняются; GUID источника исчезает; если остаток занял пустой слот, этот стек получает `NewGuid`, поскольку в один пустой слот помещена не вся стопка.
   - Поскольку D1 требует сначала заполнять совместимые стеки, наличие места в совместимом стеке приводит к слиянию даже при свободном слоте; сохранение исходного GUID в этом случае не выполняется.
3. **D8 — без TargetSlot.** Вызывающий не выбирает слот приёмника; адресное размещение (перетаскивание в конкретную ячейку UI) — будущее расширение отдельной задачей, не A11.
4. После commit исходный StackId либо отсутствует в источнике, либо отсутствует в приёмнике — никогда не в обоих (шаг 16c).
5. **Durability.** Прочность переходит вместе с предметом без изменений: HasDurability и Durability (включая неактивное значение) копируются в `Taken` как в TrySplit A10; новые стеки приёмника получают их из `Taken`; принимающие стеки сохраняют свои. Шаг 16a/16b проверяет это до commit.

**Согласование с [архитектурой §6](02_GAMEPLAY_ARCHITECTURE.md).** Архитектура задаёт три правила: «для merge сохранить GUID принимающего стека», «для split создать новый», «перенос целого стека сохраняет GUID, частичного — создаёт новый», и запрещает один StackId в двух inventories. D2 уточняет их без противоречия:

| Правило архитектуры | Применение в A11 |
|---|---|
| Перенос целого стека сохраняет GUID | выполняется, когда целый стек переходит как один стек (один пустой слот) |
| Merge сохраняет GUID принимающего стека | при переносе с объединением приоритет у этого правила: принимающие стопки сохраняют GUID, исходный GUID исчезает |
| Частичный перенос / split создаёт новый GUID | новые стеки в пустых слотах приёмника получают `NewGuid`; источник при частичном переносе сохраняет свой |
| Один StackId не может быть в двух inventories | проверяется шагом 16c и тестами 2, 3, 25 |

Формулировка «перенос целого стека сохраняет GUID» в архитектуре не оговаривала случай слияния; D2 разрешает этот случай в пользу правила merge. Оговорка D2 внесена в этом же PR в оба документа, где правило записано: §6 [`02_GAMEPLAY_ARCHITECTURE.md`](02_GAMEPLAY_ARCHITECTURE.md) и §6.3 [`15_A36_SAVEGAME_ARCHITECTURE.md`](15_A36_SAVEGAME_ARCHITECTURE.md). Проверка A36 T15 (`DuplicateStackId` между инвентарями) от этого не меняется. PR реализации A11 должен сверить фактическое поведение с этой оговоркой и описать расхождения, если они появятся.

### 3.6 Вес

- Все сравнения веса — существующие (ValidateSlots и сравнение лимита A09/A10) с допуском 1e-5; в A11 нет собственной формулы веса. Перенос не может быть строже добавления: если `TryAddExact(Taken)` в копию приёмника проходит, перенос того же Taken по весу тоже проходит (тест 36).
- Текущее состояние: перегруз любого инвентаря сверх MaxWeight + 1e-5 (например после смены профиля или фикстуры) → WeightLimit (8) на шаге 10, как «overweight state» в A10 (`a10_verify.py`). Перенос не используется как способ «разгрузить» перегруженный инвентарь; такая политика — отдельное решение вне A11.
- Кандидаты: вес источника после вычитания не растёт, но кандидат проходит ту же проверку; вес приёмника проверяется в SimulateReceiveStack/ValidateSlots тем же сравнением.
- В тестах вес сравнивается с допуском 1e-5, количества — строго. Для berry (0.1) и plank (0.4) вычисленный вес при другом разбиении стеков отличается в последнем бите (например 6×0.1 ≠ 1×0.1+5×0.1), поэтому `==` по весу ненадёжно. Нормативные границы: превышение на 1e-6 — успех, на 1e-3 — WeightLimit (как A10-M2).

### 3.7 События

- На успехе: ровно одно событие у источника и ровно одно у приёмника, каждое со своей Revision и своими ChangedSlots (по возрастанию, без повторов). Порядок рассылки в команде: источник, затем приёмник. Подписчики не должны строить логику на порядке событий между инвентарями и между вложенными командами — только на контракте потребителя ниже; тесты фиксируют фактический порядок лишь как диагностику и для доказательства сценария 30a.
- Оба события отправляются после записи **обоих** инвентарей: обработчик события источника, читая `Destination.GetSnapshot`, уже видит перенесённые предметы, и наоборот.
- Повторный вход: guard восстановлен до broadcast, поэтому обработчик может вызвать новую команду (как в A09). Следствие: если обработчик события источника изменит приёмник, подписчики приёмника получат событие вложенной команды (R+2) **раньше** события переноса (R+1). Это допустимо и должно быть задокументировано.
- **Контракт потребителя (UI и другие зеркала состояния).** Событие — только сигнал «состояние изменилось». Потребитель хранит `ShownRevision` для каждого инвентаря и при событии:
  1. если `Event.Revision ≤ ShownRevision` — ничего не меняет (устаревшее событие);
  2. иначе читает `GetSnapshot()` и применяет его, только если `Snapshot.Revision > ShownRevision`; новое `ShownRevision = Snapshot.Revision` (а не `Event.Revision`: снимок, прочитанный внутри обработчика, может быть уже новее события).
  Так более старая Revision никогда не перезаписывает показанное более новое состояние. Этот контракт обязателен для UI A16/A18; A11 обязана сделать его проверяемым тестами 30a–30e.
- Если обработчик события источника уничтожил приёмник, событие приёмника не рассылается (шаг 19): компонент уничтожается, его подписчики больше не должны отображать его состояние. Результат команды остаётся успешным — запись обоих инвентарей уже выполнена.
- На отказе: ни одного события ни у одного инвентаря.

## 4. Новые коды ошибок

**Утверждено (D3):** новые значения A11 добавляются только после всех значений, внесённых A10; значение, уже добавленное A10 с тем же смыслом, переиспользуется, а не дублируется. A10 слита и заняла номера 11–14, поэтому:

| Ситуация | Код | Происхождение |
|---|---|---|
| Нулевой, неизвестный, исчезнувший StackId или StackId только в приёмнике | `InvalidStackId` = 11 | **переиспользуется** из A10 (отдельный `StackNotFound` не создаётся) |
| Хотя бы одна ExpectedRevision не совпадает | `StaleRevision` = 15 | новый, A11 |
| Destination == Source | `SameInventory` = 16 | новый, A11 |

Номера 15 и 16 — следующие свободные после A10; окончательные значения подтверждаются при изменении enum в PR реализации повторной A05-проверкой. `SameInventory` отделён от `InvalidStackId` (которым A10 отклоняет merge стопки с собой), потому что при переносе StackId корректен, ошибочен выбор инвентаря. `EOperationError.uasset` и `BPC_Inventory.uasset` — бинарные LFS-ресурсы: менять их только в ветке реализации от актуальной main. Новые значения только добавляются в конец, существующие числа не меняются. Изменение enum требует повторить A05-проверку и обновить таблицу в отчёте.

Если пользователь запретит расширять enum: StaleRevision и SameInventory не имеют корректного существующего аналога; переиспользование (например, Busy) делает отказ неразличимым для UI контейнера (A18). Такое решение должно быть записано явно.

13. Приёмник превысит вес на одну единицу → WeightLimit.
13a. Лимит приёмника = требуемый вес − 1e-6 (фикстура как `A10SeedWeightLimit`, тип real) → успех, перенос выполнен.
13b. Лимит приёмника = требуемый вес − 1e-3 → WeightLimit (8), `unchanged2`.
13c. Текущее состояние источника перегружено сверх допуска (MaxWeight ниже текущего веса) → WeightLimit (8), как «overweight state» A10; то же для перегруженного приёмника.
14. Частично помещается (часть в стек, на остаток нет слота) → SlotsFull, ничего не перенесено.
15. Quantity 0, −1, INT_MIN → InvalidQuantity.
16. Quantity Q+1, INT_MAX → InsufficientItems.
17. Нулевой StackId при наличии пустых слотов → InvalidStackId (11).
18. Неизвестный StackId; StackId, существующий только в приёмнике; StackId, уже удалённый → InvalidStackId (11).
19. ExpectedSourceRevision −1 / +1; ExpectedDestinationRevision −1 / +1 → StaleRevision.
20. Destination == self → SameInventory.
21. Destination = None; не инициализирован; источник не инициализирован → NotReady.
21a. Два разных компонента с одинаковым InventoryId (фикстура) → NotReady.
22. Разные CatalogGameInstance → NotReady (D5).
23. Busy (фикстура выставляет guard как «чужую» незавершённую операцию):
    - 23a: guard источника = true, приёмника = false → Busy; после вызова источник **остаётся true** (чужая блокировка не снята), приёмник остаётся false;
    - 23b: guard источника = false, приёмника = true → Busy; источник false, приёмник **остаётся true**;
    - 23c: оба true → Busy; оба остаются true;
    - 23d: после каждого случая фикстура сама снимает свою блокировку, и повторный перенос с теми же ревизиями проходит успешно — доказательство, что отказ Busy не изменил ни данных, ни ревизий.
24. Повреждённое состояние источника и приёмника (нулевой/повторный GUID, Q>MaxStack, неверный индекс, неверный HasDurability) → NotReady.
25. Приёмник уже содержит стек с тем же GUID, что переносимый (фикстура) → NotReady (повреждённое состояние пары, шаг 10, до симуляции), дублирования нет.
26. Прочный предмет в приёмник без пустого слота (MaxStack=1) → SlotsFull.
26a. Revision источника = INT32_MAX (фикстура как `A10SeedRevision`), приёмник обычный → NotReady; ни один инвентарь не изменён, Revision приёмника прежняя.
26b. Revision приёмника = INT32_MAX, источник обычный → NotReady; источник **не** уменьшен (главный случай K16).
26c. Обе Revision = INT32_MAX → NotReady.
26d. Положительный: обе Revision = INT32_MAX−1 → перенос успешен, обе ровно INT32_MAX, переполнения нет; следующий перенос → NotReady.

### 6.3 Атомарность и повторный вход

27. Обработчик события источника вызывает TryRemoveExact на приёмнике: внешний результат хранит свои ревизии, итоговые количества = модель, guard обоих равен исходному (false).
28. Обработчик вызывает обратный TryTransferExact с актуальными ревизиями — успешно; с ревизиями, переданными до внешней команды, — StaleRevision.
29. Два подписчика на каждом инвентаре: каждый получает ровно по одному событию переноса.
29a. Обработчик события источника уничтожает компонент приёмника: результат переноса успешен, в журнале нет Accessed None, у источника ровно одно событие, событие уничтоженного приёмника не рассылается.
30. Порядок событий при вложенной команде записывается в результаты как диагностика. Критерии PASS тестов 27–29 не зависят от порядка: только полнота событий и Revision каждого. Единственное исключение — 30a, где обратный порядок является предпосылкой сценария и проверяется наивным слушателем, чтобы доказать, что UiMirror действительно получил устаревшее событие.

Для 30a–30e используется несохраняемый Blueprint-слушатель `UiMirror` (расширение `inventory_event_fixture.py`), который реализует контракт потребителя 3.7: хранит `ShownRevision`, `ShownSnapshotText`, журнал `(Event.Revision, Snapshot.Revision, Applied)` и счётчик `IgnoredStale`. Отдельно используется «наивный» слушатель, который записывает каждое событие, — только для доказательства, что сценарий действительно доставляет события в обратном порядке.

30a. **Обратный порядок.** UiMirror подписан на приёмник; обработчик источника (Reenter) вызывает TryRemoveExact на приёмнике. Ожидание: наивный слушатель приёмника зафиксировал Revision R+2 раньше R+1; UiMirror по итогам: `ShownRevision = R+2 = Destination.Revision`, `ShownSnapshotText` = текущий `GetSnapshot().export_text()`, событие R+1 записано как `Applied=false`, `IgnoredStale ≥ 1`.
30b. **Монотонность.** Во всём журнале UiMirror применённые `Snapshot.Revision` строго возрастают; ни одна запись с `Applied=true` не имеет Revision меньше предыдущей применённой.
30c. **Снимок новее события.** Если внутри обработчика `Snapshot.Revision > Event.Revision`, UiMirror сохраняет `ShownRevision = Snapshot.Revision`, а последующее событие с промежуточной Revision игнорируется.
30d. **Оба инвентаря.** UiMirror на источнике и на приёмнике одновременно, вложенные команды в обе стороны: итоговые `ShownSnapshotText` обоих равны их текущим `GetSnapshot`.
30e. **Отказ.** Отказ переноса (например StaleRevision) не порождает событий, и UiMirror сохраняет прежние `ShownRevision` и `ShownSnapshotText`.

### 6.4 Модель

31. Расширить модель A09 до двух инвентарей: не менее 600 случайных операций add/remove/transfer (включая stale, Quantity из {−1,0,1,2,9,20,21,INT_MAX}, неизвестные StackId, self-transfer) для трёх пар вместимостей. Модель включает прочные предметы (MaxStack=1, разные Durability) и дробный вес 0.1. После каждой операции: состояние = модель, суммы по ключу (ItemId, HasDurability, Durability) по двум инвентарям сохранены, код ошибки = модель (в том числе приоритет при нескольких нарушениях), GUID уникальны в объединении, Revision каждого = число его успешных изменений, отказ не меняет ни одного снимка.
