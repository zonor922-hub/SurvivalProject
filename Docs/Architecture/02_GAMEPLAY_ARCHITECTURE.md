# Архитектура игровых механик

Статус: проект решения, не описание уже реализованного кода. Имена классов и функций ниже — предлагаемые контракты; это не готовые функции Unreal API.

## 1. Объём первой версии и решения

Цель первого вертикального среза: игрок подбирает дерево и камень, складывает их в инвентарь, ест ягоду, создаёт доску, ставит фундамент и сундук, перекладывает ресурсы, сохраняется и получает тот же мир после загрузки.

Рабочие допущения: один локальный игрок, Windows, клавиатура/мышь, одна игровая карта. Это выбранная граница первого этапа, а не подтверждённое требование ко всей будущей игре. Количество слотов, вес, скорости истощения и рецепты — редактируемые данные. До разработки сетевого режима потребуется отдельное решение о репликации и доверии клиенту.

| Решение | Причина | Когда пересмотреть |
|---|---|---|
| Blueprint-first, Actor Components, Data Assets | В проекте нет собственного C++ модуля; можно развивать текущую основу | Профилирование показывает проблему или сложность тестирования транзакций оправдывает перенос ядра в C++ |
| Одиночный режим, команды вместо прямого доступа к массивам | Небольшой проверяемый объём; единая точка проверки | До кооператива спроектировать серверное выполнение, репликацию, RPC и ownership; сейчас этого нет |
| UMG с событиями | Уже есть UMG-зависимости; не требуется новая UI-платформа | Геймпад, сложный focus stack или множество экранов оправдают CommonUI |
| Без GAS и StateTree для потребностей | Простые числовые показатели и таймеры не требуют дополнительных подсистем | Сложные эффекты/способности или AI появятся как отдельный этап |
| Мгновенный крафт, очередь отсутствует | Не требуется хранить резервы и восстанавливать незавершённые работы | При добавлении станков/времени сначала определить резервирование, отмену, смерть и сохранение |
| Фундамент, стена, сундук; без свободного разрушения опор | Позволяет проверить строительство без сложной физики устойчивости | Перед этажами/крышами разработать расчёт графа опор и обрушение |
| Растительность остаётся декоративной | Тысячи акторов с Tick не нужны для первого среза | Добычу деревьев добавлять через отдельные ресурсные узлы, не массовую конвертацию foliage |

Не входят: бой, враги, температура, болезни, фермерство, сетевой режим, офлайн-прогресс, физическое обрушение, процедурный respawn всех деревьев, полированная анимация рук.

## 2. Размещение ресурсов

Все новые игровые ресурсы — в `/Game/Survival/`:

```text
Core/             GameMode, PlayerController, PlayerState, GameInstance, общие типы
Character/        BP_SurvivalCharacter и компоненты состояния
Interaction/      BPI_Interactable, компоненты, prompt
Items/            Definitions/, Types/, Catalog/
Inventory/        компоненты, типы операций
Survival/         потребности, профили баланса, эффекты
Crafting/         определения рецептов и компонент
Building/         определения построек, preview, итоговые акторы
World/            pickups, контейнеры, ресурсные узлы
UI/               HUD, inventory, crafting, building
Persistence/      SaveGame, DTO, миграции
Tests/            LV_SystemsTest, тестовые сценарии, fixtures
```

Существующую `/Game/Content/Survival/Maps/LV_Survival_Nature` оставить на месте. Не копировать vendor-пакет целиком. Основой нового персонажа сделать основной `/Game/ThirdPerson/Blueprints/BP_ThirdPersonCharacter` после просмотра графа: предпочтительно дочерний класс, сохраняя шаблонные перемещение/камеру. Если наследование мешает изменению графа, копирование — отдельное документированное решение с перечнем изменений. Vendor Demo не использовать как gameplay foundation.

## 3. Владение и жизненный цикл

| Владелец | Ответственность | Срок жизни |
|---|---|---|
| BP_SurvivalGameInstance | Каталог данных, загрузка/сохранение, координация смены карты | Сессия приложения; не хранит живые ссылки на акторов прошлого мира |
| BP_SurvivalGameMode | Создание игрока, respawn, последовательность восстановления | Мир; правила игры, не UI |
| BP_SurvivalPlayerState | BPC_Inventory игрока, BPC_Crafting | Состояние игрока вне Pawn; не считать автоматически переживающим любой travel |
| BP_SurvivalPlayerController | Enhanced Input, HUD, режим ввода, BPC_Interaction, BPC_Building | Контроллер локального игрока; перепривязка при possession |
| BP_SurvivalCharacter | BPC_Survival, locomotion, здоровье, визуал | Текущее тело; при respawn создаётся заново |
| BP_WorldPickup | Stack, WorldEntityId, доступность подбора | Мировая сущность; исчезает только после подтверждённого переноса |
| BP_StorageContainer | Собственный BPC_Inventory, BPI_Interactable, WorldEntityId | Мировая сущность, сохраняется |
| BP_BuildPiece | BuildDefinitionId, transform, WorldEntityId, support links | Мировая сущность, сохраняется |
| WBP_* | Представление снимка данных и отправка команд | Экран; не источник истины |

Инициализация: GameInstance загружает и валидирует каталог → GameMode создаёт PlayerState/Pawn → Controller получает ссылки после possession → компоненты явно Initialize → UI подписывается → разблокируется ввод. При загрузке сначала восстановить мир, затем инвентарь/показатели, затем включить таймеры и UI. Ни один компонент не должен «угадывать» готовность другого по Delay(0.2).

При смерти: остановить действия, закрыть UI, отменить preview; в первом срезе инвентарь сохраняется в PlayerState, потребности сбрасываются по профилю, GameMode возрождает тело у PlayerStart. Потеря вещей/могила — будущая политика. При travel состояние переносить через Save DTO, а не предположение о выживании PlayerState.

## 4. Типы данных

Каталог хранит явный стабильный ID типа `Name` (`item.wood`, `recipe.plank`, `build.foundation`). Переименование файла не меняет ID. ID не равен DisplayName и не строится из пути. Нельзя переиспользовать удалённый ID для другого предмета.

| Тип | Поля и ограничения |
|---|---|
| PDA_ItemDefinition | ItemId, DisplayName/Description (Text), Icon soft ref, WorldMesh soft ref, MaxStack≥1, UnitWeight≥0, Category enum, ConsumableEffectId optional, DurabilityMax optional |
| FItemStack | StackId GUID, ItemId, Quantity int>0, Durability optional; одинаковый ID и состояние нужны для объединения; предметы с индивидуальной прочностью в MVP MaxStack=1 |
| FInventorySlot | SlotIndex и optional Stack; пустой слот не имеет Quantity=0 stack |
| FInventorySnapshot | InventoryId, Revision int, Slots, MaxWeight; CurrentWeight вычисляется из данных, не независимый источник истины |
| FOperationResult | Success, ErrorCode, ActualQuantity, NewRevision; при ошибке ActualQuantity=0 |
| FInteractionOption | ActionId, Prompt Text, Enabled, DisabledReason; данные для UI без изменения объекта |
| PDA_RecipeDefinition | RecipeId, Ingredients[{ItemId,Quantity}], Outputs[{ItemId,Quantity}], StationType optional; количество только целое положительное |
| PDA_BuildDefinition | BuildId, ActorClass soft ref, PreviewMesh, Cost[], Footprint/placement shape, MaxSlopeDegrees, support type, sockets, AllowedOnWater=false |
| FWorldEntityRecord | EntityId GUID, Kind, DefinitionId, Transform, StateVersion и типизированное состояние |
| SG_SurvivalSave | SaveVersion, ContentVersion, MapId, Player DTO, WorldRecords[], RemovedAuthoredIds[] |

Для Blueprint MVP — явный PDA_GameCatalog со списками Data Assets и таблицей ID→definition, которую GameInstance строит при старте. Валидация ловит дубликаты и отсутствующие ссылки. Soft references должны попасть в cook через Asset Manager/Primary Asset Labels либо явный проверенный список. Сам факт появления в редакторе не доказывает включение в сборку.

Пример тестовых данных (баланс предварительный): wood MaxStack=20, weight=0.5; stone 20/1.0; berry 10/0.1; plank 20/0.4. Recipe plank: 2 wood → 1 plank. Foundation: 4 plank + 2 stone. Inventory fixture: 4 слота, MaxWeight=10; реальные параметры игрока задаются отдельным профилем.

## 5. Взаимодействие

`BPI_Interactable` предлагает `GetInteractionOptions(Context)` и `ExecuteInteraction(Context, ActionId) -> Result`. Context содержит инициатора, актуальный Pawn и идентификатор цели. UI не передаёт доверенное количество награды или стоимость.

BPC_Interaction выполняет trace из камеры с ограниченной частотой (начальная настройка 10 Hz) и хранит только текущий focus. Дальность выполнения измеряется от персонажа до точки взаимодействия (например 250 cm), чтобы камера за спиной не позволяла дотянуться дальше. При нажатии снова проверяются range, line of sight, существование, доступность и состояние персонажа. Проверка фокуса сама ничего не подбирает.

Предлагаются trace channels `Interaction` и `BuildPlacement`. Стены должны блокировать взаимодействие даже без интерфейса; foliage-декор по умолчанию игнорировать, отдельно интерактивные ресурсы блокируют. На действия под водой/при открытом меню влияет политика Controller, а не каждый widget отдельно.

WorldPickup запрашивает TryAddExact. При полном инвентаре остаётся в мире с прежним количеством. На успехе помечается consumed, затем удаляется. Повторное нажатие на consumed-объект возвращает AlreadyConsumed. Сундук открывает UI после range/LoS; при отходе закрывается, а каждая transfer-команда перепроверяет расстояние.

Мост к vendor-сундуку может использовать его меш/анимацию, но новая логика и интерфейс принадлежат игре. Не выдавать loot только по завершению анимации: gameplay-команда должна иметь независимый результат.

## 6. Инвентарь и целостность операций

Публичные команды BPC_Inventory:

- GetSnapshot; CanApply(ChangeSet) без мутации;
- TryAddExact(ItemStack), TryRemoveExact(ItemId, Quantity);
- TrySplit(StackId, Quantity, TargetSlot), TryMerge(SourceStackId, TargetStackId);
- TryTransferExact(Source, Destination, StackId, Quantity, ExpectedRevisions);
- TryApplyRecipe(RecipeId), ConsumeItem(StackId), запрос стоимости строительства через общий координатор.

`Exact` означает «всё или ничего». Частичный подбор сознательно отсутствует в MVP. Сначала объединять совместимые стеки, затем занимать пустые слоты в порядке индексов. Для merge сохранить GUID принимающего стека; для split создать новый. Перенос целого стека сохраняет GUID, частичного — создаёт новый. Не должно быть одного StackId одновременно в двух inventories.

Каждая команда: проверить положительность/ID/ревизии → поставить mutation guard → рассчитать копии затронутых inventories → проверить слоты, стеки и вес результата → применить все копии → увеличить ревизии → снять guard → отправить события. До commit никаких UI/event callbacks. В критической секции нет Delay, asynchronous load или latent nodes. Все definitions загружены заранее.

При ошибке ни один inventory не меняется; Events не сигнализируют об успехе. Событие `OnInventoryChanged(Revision, ChangedSlots)` публикуется после commit. UI запрашивает новый snapshot и не хранит изменяемую копию как истинное состояние.

Для transfer проверять оба ExpectedRevision. Для команд мира добавляется guard сущности. Blueprint execution на одном потоке само по себе не защищает от повторных событий и latent-вызовов — их исключает контракт. Сетевой режим потребует серверного координатора и idempotency, которых здесь ещё нет.

Вес считается с небольшой числовой погрешностью для float, количество — строго int. Reject: неизвестный предмет, qty≤0, превышение веса/слотов, несовместимое состояние, устаревшая ревизия, повторная занятая операция. Нельзя silently clamp выдачу ресурсов.

## 7. Выживание и использование предметов

BPC_Survival содержит Health, Hunger, Thirst, Stamina в диапазоне [0,Max]. Профиль задаёт начальные значения, drain/recovery rates и damage. Единицы: пункты/секунду игрового времени. Timer, например 0.25 s, использует фактический прошедший игровой интервал; пауза не истощает показатели. UI обновляется событиями, не binding-опросом на каждом кадре.

Hunger/Thirst=0 наносят периодический damage один раз по формуле; не создавать несколько параллельных таймеров. Health=0 вызывает смерть ровно один раз. Stamina расходуется на sprint, при нуле sprint прекращается; восстановление после настраиваемой задержки. После respawn старые делегаты/таймеры не должны работать.

`ConsumeItem` валидирует effect и состояние персонажа, рассчитывает новый snapshot потребностей и inventory. При полном целевом показателе возвращать NoEffect без списания (для MVP без многокомпонентных сложных эффектов). Списание одной единицы и эффект применяются в одной синхронной операции, события только после обоих изменений. Анимация/звук — следствие успеха, не способ провести операцию.

Вода: сначала проверить переходы CharacterMovement Walking→Swimming→Walking, вход/выход с разных берегов, удержание у поверхности и управление по вертикали. `WaterBodyLake` визуализирует воду; нельзя по одному мешу считать плавание реализованным. Подводный кислород, урон от утопления и качество питьевой воды вынесены за MVP. «Выпить воду» не означает добавлять воду в любой открытый inventory без предмета/рецепта.

## 8. Крафт

BPC_Crafting получает RecipeId, читает рецепт из каталога, проверяет доступность станции (если требуется), состояние игрока и входы. В MVP — ручной мгновенный крафт, одна операция за команду; UI-кнопка не списывает материалы.

Вычисляется итоговый inventory **после** удаления ингредиентов и добавления результатов. Освободившиеся слоты можно использовать под результат. При нехватке места возвращается OutputCapacity, ингредиенты остаются. Подсчёт одинаковых ingredients предварительно агрегируется по ItemId. Любая ошибка каталога блокирует рецепт.

Если позже появятся timed jobs: состояние Idle→Reserved→Running→Ready→Claimed/Cancelled; ингредиенты переходят в отдельный escrow, итог не теряется при полном inventory, отмена возвращает через гарантированное хранилище. Понадобятся JobId, save schema и политика смерти/ухода от станции. Не добавлять один Delay в текущую atomic-команду.

## 9. Строительство

BPC_Building управляет выбранным BuildId, preview transform и поворотом. Preview не сохраняется, не расходует предметы, не влияет на физику и не блокирует собственные trace. Tick допустим только пока preview активен.

Проверки размещения:

1. Каталог и класс готовы; персонаж жив, находится в разрешённом режиме и в пределах BuildRange.
2. Есть точка поверхности; slope вычислен из normal; фундамент стоит на допустимом грунте.
3. Полный footprint проверен shape overlap/sweep, а не одним центральным лучом. Pawn, камни, деревья и другие здания блокируют.
4. Вода и зона озера запрещены для footprint, не только pivot. До надёжного water query использовать явную `BP_NoBuildZone` вокруг озера, включающую береговой запас; это gameplay-зона, не swim PhysicsVolume.
5. Для стены необходим свободный сокет существующего фундамента. Опора исключается из overlap лишь в разрешённой области соединения, а не целиком из любых проверок.
6. Стоимость доступна; при подтверждении все проверки выполняются заново.

Commit: guard → повторная валидация → рассчитать inventory после стоимости → создать неактивный actor с отключённой коллизией/интеракцией и без побочных эффектов BeginPlay → если spawn неуспешен, ничего не списывать → commit inventory и запись EntityId → Activate → события. Activation должна быть простой гарантированной операцией после полной подготовки. Если подготовка акторов не может обеспечить это, сначала переработать lifecycle, не компенсировать произвольные побочные эффекты «возвратом ресурсов».

Строение хранит стоимость, реально оплаченную при создании (для возможного будущего возврата), GUID и support/socket links. В MVP демонтаж без возврата материалов, запрещён для опоры с зависимыми постройками и непустого сундука. UI показывает это до подтверждения. Это выбранная простая политика, меняется отдельным решением.

## 10. Ресурсы мира и масштаб

Не превращать всю траву, деревья и камни карты в Blueprint Actors. Начать с нескольких `BP_ResourceNode` в тестовой зоне. Node имеет стабильный ResourceId, RemainingYield, cooldown (если позже нужен), definition награды. Сбор выдаёт ресурс только после успешного добавления в inventory; при полном inventory узел не истощается.

Для будущей добычи foliage понадобится слой соответствия стабильного ResourceId и экземпляра/transform. Индекс HISM/Foliage instance нельзя использовать как постоянный Save ID: удаление/перестройка может изменить индексы. В первом этапе существующая массовая расстановка — декор, новые узлы — явно размещённые gameplay-акторы.

Контейнер использует тот же inventory-компонент. Открытие крышки не создаёт новый набор loot при каждом входе. Стартовое наполнение выполняется ровно один раз для новой сущности и отключено при загрузке сохранения.

## 11. Сохранение

SaveCoordinator в GameInstance формирует DTO, а не сериализует живые Actor references. WorldEntityId назначается авторским объектам при подготовке уровня, а динамическим при создании; не генерировать новый ID каждый BeginPlay. У authored pickups после подбора сохраняется tombstone ID, иначе они появятся снова при загрузке карты.

В snapshot входят: map identifier, transform игрока, показатели, inventory и slot/stack IDs, records динамических pickups/containers/buildings, содержимое контейнеров, depleted resource nodes, удалённые authored entities. Support links сохраняются по GUID. Не сохранять preview, виджеты, ссылки на PlayerController, transient focus.

Запись возможна только между синхронными операциями, в состоянии Ready. Для MVP один manual save; второй save/load запрещён до завершения первого. Сначала snapshot и проверка ссылок/версии, затем запись нового слота поколения, проверочное чтение, затем переключение manifest active generation. Предыдущий валидный слот остаётся fallback. При сбое manifest загрузка выбирает последний валидный snapshot по generation. Не обещать атомарность обычной перезаписи одного файла.

Загрузка: проверить schema и map → открыть мир → остановить gameplay update → применить tombstones к authored objects → создать dynamic actors без стартового loot → восстановить inventories, survival, transform → связать support links → проверить уникальность ID и целостность → Activate → подписать UI/разрешить ввод. Повторное применение того же snapshot не должно удваивать actors.

SaveVersion новее поддерживаемой: не загружать и не перезаписывать. Неизвестный ItemId/BuildId в MVP — ошибка совместимости с выбором прошлого сохранения, без молчаливой потери вещей. Миграция каждой версии — отдельная функция с тестовым fixture. Смерть сбрасывает показатели по политике, загрузка восстанавливает их из DTO: это разные сценарии.

## 12. Проверка и эксплуатационные ограничения

`LV_SystemsTest` содержит плоский пол, стену для LoS, 2 pickups, контейнер, ресурсный узел, наклонную поверхность, no-build zone и spawn point. Фикстуры inventory создаются из одних и тех же данных. Проверки результата читают snapshot/DTO, а не только визуально оценивают HUD.

| Инвариант | Обязательная проверка |
|---|---|
| Вещи не дублируются | Двойной interact, transfer с устаревшей revision, повторная load |
| Ошибка не меняет состояние | Нехватка веса, слотов, ингредиентов, невалидный spawn |
| Крафт сохраняет баланс | Итог = вход − ingredients + outputs; нет промежуточного публичного состояния |
| Строительство платное ровно один раз | Валидная установка списывает один cost, invalid/cancel — ноль |
| Состояние переживает respawn | Inventory сохраняется, показатели сбрасываются, delegates не удваиваются |
| Сохранение полное | Сравнить inventories, IDs, transform с допуском, support links, tombstones до/после |
| UI не управляет истиной | После закрытия/открытия snapshot тот же; удалённый target обрабатывается безопасно |
| Работает вне редактора | Windows Development build стартует нужной картой, definitions/иконки/меши доступны |

Бюджет производительности определяется замером на машине пользователя, а не обещанием 60 FPS. Записать baseline frame time CPU/GPU на природе и тестовой карте, число actors, активных timers и trace frequency. У inventory/craft/survival нет Tick на каждом предмете. Вводить оптимизацию только по измеренному узкому месту.
