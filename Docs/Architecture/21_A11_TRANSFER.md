## Реализация и разрешения

TryTransferExact переносит количество целиком либо возвращает отказ без изменения обоих компонентов. Проверяет готовность, идентичность/каталог, оба guard, предел и ожидаемые Revision, количество/StackId в утверждённом порядке. Сохраняет исходные guard; моделирует локальные кандидаты обеих сторон; проверяет слоты, вес, Integer64-агрегаты и уникальность GUID пары. Записывает оба состояния, восстанавливает оба guard, отправляет событие источника, затем действительного приёмника. При уничтожении приёмника callback источника второе событие пропускается. Возвращаемые ревизии внешней команды кэшированы. На отказе кандидаты отбрасываются, guard восстанавливаются; частично записанного состояния нет.

Полный стек в единственный новый слот сохраняет GUID. Partial получает новый GUID; при merge сохраняются GUID принимающих стеков, исходный GUID целого стека исчезает, остаток после merge получает новый GUID (D2). Перегруженный источник можно разгружать без увеличения веса. Приёмник обязан соблюдать лимиты. В конец EOperationError добавлены StaleRevision=15 и SameInventory=16, значения0–14 сохранены.

Первое разрешение: общий private CheckReceiveExact для TryAddExact и SimulateReceiveStack. Helper не изменяет поля/Revision/GUID и не отправляет события; сохраняет две фазы, порядок проверок и приоритет ошибок A09. Const-флаг не добавлен из-за существующего non-const ValidateSlots; отсутствие эффектов проверено графом/runtime-снимком. Публичные контракты A09/A10 не менялись.

Второе разрешение: только в локальном кандидате A11 восстанавливается Durability существующего стека приёмника с HasDurability=false, количество которого выросло при merge. Значение берётся до симуляции: **80 → 37 → 80**. Активная Durability, новые стеки и остальные поля этим исключением не затрагиваются. Тест36 допускает только это отличие от A09, остальные поля сравнивает строго, GUID — по D2. SimulateAddExact и CommitInventory не редактировались; другие игровые системы и A36 не менялись. [Сохранённая компиляция/сравнение десяти графов последнего патча](evidence/a11_durability_implementation.json), [исключения к §3.3 и тесту36](17_A11_DESIGN_PROPOSAL.md).

## Закрытие25c и40 (29.10.2026)

25c теперь содержит40 двусторонних переносов. C содержит wood и два активных durable-предмета37/80. После каждого вызова проверяются полный export_text C, ноль событий C и глобальная уникальность GUID трёх инвентарей. Контрольная коллизия GUID с C остаётся ожидаемо необнаруженной по K25; это не положительная проверка глобальной защиты.

40 выполняется в единственной Python-обёртке transfer, через которую проходят все прямые вызовы TryTransferExact сценариев suite. Временный Blueprint-listener сохраняет собственный и встречный snapshot в отдельных массивах до reentry. На успехе сравниваются обе committed Revision, точные keyed-дельты сторон, суммы, GUID и побитовое представление Durability каждого сохранившегося стека; новые стеки сверяются с переносимым. Посторонние слоты с прежним GUID/Quantity сравниваются целиком. Затем проверяется состояние после вложенных команд с учётом реальных Remove callbacks и сохранность metadata. При уничтожении приёмника используется сохранённый снимок из события до DestroyComponent, без вызова на уничтоженном объекте. На отказе оба полных снимка и guard неизменны, событий нет. Архитектурные исключения не расширялись; игровые SHA прежние.

Отладка аудитора выявила только две ошибки тестовой инструментализации: сравнение Unreal Guid как Python-объекта вместо значения и общий индекс для журналов с разным числом записей. Исправлены сравнением export_text и отдельными индексами; требования тестов не ослаблены. Неуспешные локальные прогоны не включены в итоговый PASS.
