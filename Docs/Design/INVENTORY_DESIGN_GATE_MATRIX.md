## 1. Уровни достоверности

- **GAME RULE AGREED** — владелец явно описал ожидаемое игровое поведение; реализация может отличаться.
- **PROPOSAL** — технический/балансовый вариант для обсуждения, не разрешение писать код.
- **OPEN DECISION** — без решения владельца система не может получить статус DESIGN APPROVED.
- **CURRENT CONTRACT** — точно задокументированное поведение существующей базы, которое пока запрещено молча заменять.
- **NOT VERIFIED LOCALLY** — локальные изменения A17.1 не исследованы облачным аудитом.

## 3. Вопросы для окончательного утверждения (упорядочены по влиянию)

| ID | Блокирующий вопрос | Рекомендуемый вариант, не утверждённый владельцем | На что влияет |
|---|---|---|---|
| D01 | Есть ли **абсолютный** потолок веса сверх нормальной грузоподъёмности? | Начать без игрового абсолютного потолка; оставить защиту невалидных чисел/переполнения. Альтернатива: отдельная HardCapacity | A09, A11, подбор A15, A36 load, UI |
| D02 | Что означает «3 в новый слот» при Merge `15+8→20+3`? | Перемещать 5 из второй стопки в первую; остаток 3 остаётся во второй существующей ячейке. **Но пользователь буквально сказал «в новый слот»: третий физический слот не отвергать без явного уточнения.** | A10, A17.1, слот-full сценарий, GUID |
| D03 | Какая стартовая вместимость и скорость персонажа? | Балансировать после вертикального среза; 24 слота/40 ед. веса — лишь ранний пример | Профили, HUD, тестовые фикстуры |
| D04 | Сам рюкзак — автономный физический inventory с InventoryId? | Да; PlayerState содержит ссылки на экипированную сумку, у неё собственные слоты и GUID | A08, A11, A18, A36, world-drop |
| D05 | Можно ли хранить полный рюкзак в сундуке или поднимать на персонажа полный второй рюкзак? | Один экипированный; запрещены вложенные полные сумки до модели контейнеров | Уникальность, Save DTO, дублирование |
| D06 | Как комбинировать штраф большого рюкзака, перегруз и нулевую стамину? | Независимые мультипликаторы скорости с нижним ненулевым пределом | CharacterMovement, A21 |
| D07 | Что такое «активная угроза»? | Реальное преследование/полученный урон/боевой режим; простая близость врага не закрывает UI | ИИ, UI, прерывание drop |
| D08 | Что считается безопасным размещением сброшенного рюкзака? | Проверка collision/navmesh/вода/недоступность позиции до commit | World entity, плавание, SaveGame |
| D09 | Условия автоматической разгрузки | Только собственные доступные сундуки в радиусе, с фильтрами; все успешные одиночные переносы сохраняются | A11, A18, инвентарь у базы |
| D10 | Должен ли хотбар ссылаться на конкретный StackId либо на категорию ItemId? | Для инструмента на StackId + InventoryId; расходники могут иметь разрешённый fallback по ItemId | A10 Split/Merge, A17, A19 |
| D11 | Особые свойства хранения и скоропортящиеся стаки | Не смешивать свежесть/свойства без заданного правила; отдельные поля состояния экземпляров | A05, Stack equality, A36 |
| D12 | Как работает сеть Эха: доступ ко всем сундукам или только в пределах Узла? | Локальная сеть связанных хранилищ, постройки не могут тратить ресурсы из неактивных сетей | Атомарный крафт, Сейв, узлы |

**Важная оговорка по D02:** результат `20+3` согласован, а «новый слот» в исходной формулировке и «остаток в старом исходном слоте» из последующей интерпретации не тождественны. Требуется зафиксировать одно из двух поведений **до** утверждения новой реализации Merge, а не выбирать его молча.

## 4. Конфликты с уже существующими техническими контрактами

| Контракт в опубликованном main | Противоречие будущему дизайну | Требуемый Design Change |
|---|---|---|
| A08: `MaxWeight` и private Slots, InventoryId, Revision | Нужны носимая нормальная масса и отдельные сумки | Новые источники вместимости, без прямого доступа UI |
| A09: `TryAddExact` запрещает превышение WeightLimit | Добровольный перегруз требует успешного подбора | Явный новый валидатор/политика приема; старые fixture тесты не переписывать без аналога |
| A10: `TryMerge` full-only, отказ при MaxStackExceeded | 15+8 должно давать 20+3 | Новая команда или versioned изменение после Design Gate; регрессия старого API |
| A10: `TrySplit(StackId, Quantity, TargetSlot)` | Игрок не указывает TargetSlot | UI/координатор выбирает слот, текущий API может остаться |
| A11: `TryTransferExact` проверяет WeightLimit приёмника и ревизии обеих сторон | При перегрузе часть операций легальна, а рюкзак становится отдельным inventory | Отдельная receiver policy для player/bag/storage; не ломать атомарный commit двух сторон |
| A36 §4.2, §10.2: `FSave_Inventory.MaxWeight` и **вес ≤ MaxWeight при загрузке** | Перегруженный инвентарь станет невозможным к загрузке по текущей схеме | Новый DTO/SaveVersion или явно совместимая миграция, валидатор и тесты старых файлов |
| A36: `FSave_EntityKind` не описывает экипированный и сброшенный полный рюкзак | Нужно сохранить мировой рюкзак с вложенным инвентарём | Схема world record + equipment ownership + migration |
| A05: `FItemStack` без свежести/резонанса | Особое хранение меняет состояние предмета | Не вводить по одному непроверенному полю; отдельно тип/версия данных и equality |
| A19: UI lifecycle после Pawn change | Ссылки хотбара/рюкзака должны переживать respawn безопасно | Unbind/Rebind, не держать dangling Actor refs |
| A41: вертикальный срез до будущего сюжета | Механика Узлов Эха ещё концепт | Не блокировать основной инвентарь поздней магической сетью |

**Отдельная опасность:** новый policy должен различать `NormalCarryCapacity` (порог штрафов), `HardReceiveLimit` (если будет утверждён) и физические лимиты **каждого** контейнера. Применять одну общую переменную `MaxWeight` ко всем ролям без классификации запрещено на этапе проектирования.

## 5. Рекомендуемая модель данных (только вариант для обсуждения)

```text
PlayerState
  OwnedProgression: Strength, Endurance
  BaseInventoryId -> InventoryComponent (existing, PlayerState)
  EquippedBackpackId? -> BackpackRecord
  EquippedBeltId? -> EquipmentRecord
  Hotbar: slots -> (InventoryId, StackId, optional ItemId fallback)

BackpackRecord
  EntityId (physical item, when world object exists)
  InventoryId (contents, stable across equip/drop/re-equip)
  DefinitionId (backpack type)
  Slots / Revision (same atomic inventory ownership rules)

CarryingSnapshot (derived, not independent source of truth)
  TotalWeight = base slots + equipped backpack contents + equipped items + backpack item mass
  NormalCapacity = from Strength / modifiers
  IsOverloaded = TotalWeight > NormalCapacity (+ numeric epsilon policy)
  Stamina / Movement = from A20/A21 / movement policy

World
  DroppedBackpackEntity { EntityId, InventoryId, transform }
  CartEntity { EntityId, InventoryId, transform, attach/movement state }
  EchoNode { NodeId, links, active }
```

- Не создавать actor-ссылок в Save DTO.
- GUID нельзя дублировать при смене владельца; в мире и в экипировке одновременно не должно существовать две авторитетные копии одного рюкзака.
- Не вкладывать инвентарь как копию в поле обычного ItemStack; это создаёт двусмысленное владение. На дизайн-ревью определить нормализованные ссылки и lifetime.
- Рюкзаки и тележки требуют реестра EntityId/InventoryId; техническое подключение к A36/A37–A40 проектируется **до** реализации.
- UI читает snapshots; даже preview предполагаемого результата не изменяет состояние.
- При отказе операции количество/GUID/Revision/мировые сущности не меняются.

## 8. Условия перехода из DRAFT в APPROVED

Нужны: явное решение владельца по D01–D12 (разрешено дробное утверждение по подсистемам), окончательная модель владения рюкзаком, policy Receive/Weight для игрока/контейнеров, список новых DTO + SaveVersion/migration, тесты I01–I30 с ожидаемыми исходами, отдельный план реализации и статус A17.1.

**До этого момента никакая новая механика не считается разрешённой к реализации.**
