# SurvivalProject — постоянные правила работы и публикации

Проект: стилизованная Survival-игра на Unreal Engine 5.8.4. Следовать архитектуре и небольшим задачам из `Docs/Architecture/`. Учитывать существующие системы, не создавать дубликаты и не менять несвязанные игровые ресурсы. Объяснения и инструкции проверки давать на русском языке с названиями меню русского интерфейса Unreal Engine.

## Завершение задачи

- После каждой завершённой задачи обновлять `Docs/ProjectStatus.md` — единственный основной файл текущего прогресса проекта — и соответствующий отчёт в `Docs/Architecture/`. Не создавать дублирующий корневой `ProjectStatus.md`; не объявлять устаревшие сведения проверенными.
- Указывать номер задачи, зависимости, изменённые файлы, проведённые проверки, их результаты и оставшиеся ограничения. Различать «в работе», «реализована, не проверена» и «завершена».
- Выполнять доступные проверки до публикации: проверку области изменений, Blueprint-компиляцию, соответствующие контрактные/PIE-тесты и сборку, когда она требуется критериями задачи. Для документации проверять содержание, ссылки и diff; запуск Unreal не требуется.
- Не отмечать непроверенные задачи завершёнными. Если необходимая проверка недоступна или не прошла, записать причину и остановить публикацию задачи.

## Изоляция работы

- Разрабатывать в отдельных ветках и публиковать завершённые задачи через Pull Request в `main`. Не отправлять изменения напрямую в `main`, не сливать PR автоматически без отдельного разрешения.
- При наличии незавершённой работы использовать отдельный чистый worktree от актуального `origin/main` или от явно проверенной ветки завершённых зависимостей. Не публиковать исходную ветку целиком.
- Сохранять пользовательские локальные изменения и промежуточные коммиты. Не выполнять reset, rebase, force push или удаление коммитов для очистки публикации. Перед разделением накопленной работы сохранять резервную ссылку на исходный HEAD.
- Добавлять в индекс только явно перечисленные файлы задачи. Не использовать без разбора `git add .`, `git add -A`, `git commit -a`, `git push --all`, `git push --mirror` или отправку всех тегов. Не публиковать резервные ветки.
- Не включать чужие правки, незавершённые Blueprint, карты, временные генераторы, локальные резервные копии, секреты, токены и выходные данные Unreal. Не считать файл безопасным только потому, что он уже закоммичен.

## Обязательная проверка перед каждым push

1. Выполнить fetch; при ошибке доступа или невозможности установить актуальную базу остановиться.
2. Проверить `git status`, текущую ветку, remote, подготовленный diff и точную целевую ветку. Не менять чужое рабочее дерево.
3. Просмотреть **всю исходящую историю**, а не только последний коммит: `git log --reverse --oneline origin/main..HEAD`, `git diff --name-status origin/main...HEAD` и изменения каждого исходящего коммита. Для PR с другой базой дополнительно проверить диапазон относительно этой базы.
4. Сопоставить каждый исходящий коммит с завершённой задачей и её проверками. Проверить зависимости и отсутствие непреднамеренных файлов. Если среди исходящих коммитов есть незавершённая, непроверенная или неидентифицированная задача — **остановить публикацию всей ветки**, даже если её изменения отменены последующим коммитом.
5. Отправлять только проверенные и завершённые изменения явным refspec в одну ветку; затем создать PR. Не обходить Git LFS и его pre-push проверку для Unreal-ресурсов.
6. Проверить SHA опубликованной ветки и состав PR на GitHub. После публикации сообщить ссылку на PR/ветку и полный SHA коммита, результаты проверок и ограничения. При неудаче сообщить фактическую ошибку, не заявлять об успешной публикации.

## Известная накопленная работа

Локальная `main` на момент введения правил содержит шесть неопубликованных коммитов после `c312370a995df11e5f0f5c7b66eeb70f83051da6`: A05 `aada215`, A06 `daffec3`, A07 `faaed61`, незавершённая A08 `2eea6d5`, A24 `c97f449`, сводная документация `1e3c750`. Не отправлять эту ветку или её резервную копию. Сначала отдельно проверить и перенести только завершённые задачи в чистые ветки; не переносить общую документацию целиком, если она описывает исключённые изменения.

## Границы автоматизации

Эти инструкции задают обязательный процесс для ИИ-разработчика после завершения задачи. Они не являются фоновым сервисом, Git-хуком или технической блокировкой ручного push. Не создавать безусловную отправку при каждом сохранении/коммите. Автоматическое обновление означает проверенный коммит в отдельной ветке и PR, а не автоматическое слияние в `main`.

Первичное введение правил — согласованное исключение: ветка настройки публикует только этот `AGENTS.md`, без изменения `Docs/ProjectStatus.md`, игровых отчётов и игровых изменений. Это исключение не распространяется на последующие задачи.
